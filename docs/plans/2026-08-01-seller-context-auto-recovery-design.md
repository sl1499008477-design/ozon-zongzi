# Seller 上下文自动恢复设计

## 背景与根因

扩展重装、更新或重新加载后，已经打开的 `seller.ozon.ru` 页面不会必然重新注入扩展的内容脚本。当前 Seller 登录态仍然有效，但扩展后台拿不到页面真实请求里的公司编号。为避免跨账号或跨店铺读取，现有安全策略会拒绝继续调用 Seller 商品接口，最终表现为：

- 数据面板提示“部分商品数据加载失败”；
- 点击采集提示“Ozon 商品资料暂时无法读取”；
- 类目、重量、长度、宽度和高度为空。

刷新 Seller 页面后数据恢复，已在真实商品页验证，因此本次只修复扩展生命周期后的上下文恢复，不改变采集数据来源。

## 目标与验收标准

用户主动打开数据面板或点击采集时，如果 Seller 页面已打开且已登录，但公司上下文尚未建立，扩展应自动恢复并继续原操作。

验收标准：

1. 只刷新一个可信的 Seller 顶层标签页，优先当前活跃页。
2. 最多自动刷新一次，并在限定时间内轮询上下文；不得循环刷新。
3. 同时发生的多个读取请求共用同一次恢复过程，不得重复刷新。
4. 没有 Seller 页面、检测到多个公司编号冲突或恢复超时时，必须失败关闭并给出明确原因。
5. 恢复成功后，原采集流程能继续得到类目、重量、长度、宽度和高度。
6. 不新增店铺同步指令，不修改数据库、后端 API、采集箱归属或权限边界。

## 方案

在 `seller-company-context-runtime` 中新增 `resolveCurrentWithRecovery()`。它先执行原有只读解析；仅当错误为 `SELLER_CONTEXT_REQUIRED` 且存在可信 Seller 页面时，刷新一个标签页、等待内容脚本重新上报公司编号，然后重试解析。

恢复过程使用单个共享 Promise 合并并发请求。成功、失败或超时后都清理共享状态。公司编号冲突、无 Seller 页面等情况不触发刷新，沿用现有安全策略。

后台数据面板预检和 Seller 商品查询统一使用该恢复入口。现有 `resolveCurrent()` 保持不变，供不允许产生页面刷新副作用的检查使用。

## 错误处理

- 无 Seller 页面：`SELLER_CONTEXT_REQUIRED`，提示先打开并登录 Seller。
- 自动恢复超时：`SELLER_CONTEXT_RECOVERY_FAILED`，提示自动恢复失败并建议手动刷新 Seller。
- 多公司编号冲突：`SELLER_COMPANY_CONTEXT_CONFLICT`，不刷新页面，提示只保留当前经营公司的 Seller 页面。
- 其他异常：原样向上抛出，不伪装为商品不存在。

## 测试与回归

先补失败测试，再实现：

- 缺少上下文时只刷新活跃 Seller 页一次，随后解析成功；
- 并发解析只触发一次刷新；
- 无 Seller 页、冲突和超时均不循环刷新；
- 原 `resolveCurrent()` 合同和现有 Cookie/页面观测策略不变；
- 打包后的扩展副本与源码一致；
- 在真实 Seller 与 Ozon 商品页上验证数据面板和采集按钮。

## 回滚

回滚 `seller-company-context-runtime.js`、后台的两个调用点及对应测试即可恢复旧行为。没有数据库迁移、数据写入或接口变更，不需要数据恢复。
