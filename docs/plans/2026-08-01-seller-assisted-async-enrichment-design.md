# Seller 登录辅助的 Ozon 商品异步补全设计

日期：2026-08-01
状态：已确认，待实施

## 1. 业务目标

用户在 Ozon 商品页点击“采集”后，公开商品资料应立即进入账号级统一采集箱。类目、包装重量、包装长宽高暂时无法读取时，采集不能整体失败；Web 后端应创建幂等补全任务，由同一浏览器中的扩展借用当前 Seller 登录状态读取缺失资料。

用户在 Seller 中切换店铺后，扩展应自动识别新的 Seller Company ID。上下文缺失时，扩展可以安全恢复，但不得强制刷新用户正在操作的 Seller 页面。商品资料完整前允许查看、编辑和保存，不允许提交上架。

## 2. 验收标准

1. 点击采集后，标题、图片、价格等公开资料立即写入当前 Web 账号的采集箱。
2. 类目、重量或尺寸缺失时，采集结果显示“资料补全中”，而不是“采集失败”。
3. 同一账号、同一 Ozon SKU 的重复采集不会创建重复商品或并行重复补全任务。
4. Seller 已登录且扩展在线时，补全任务自动读取类目、重量和包装长宽高，并更新原采集商品。
5. Seller 未登录、扩展离线或 Ozon 临时失败时，商品保留，任务可恢复并自动重试。
6. Seller 切换店铺后，扩展自动识别新的 Company ID；切换期间的旧请求结果不得写入。
7. 扩展不得刷新或关闭用户创建的 Seller 页面；恢复需要页面时，只能管理扩展自己创建的非激活恢复页。
8. 补全结果只填写仍为空的字段，不覆盖用户已经手动填写的类目、重量或尺寸。
9. 原始 Ozon 类目证据与目标经营店铺的上架类目分开保存。
10. 类目、重量、包装长宽高不完整时，后端上架门禁必须拒绝提交。
11. Seller Cookie、密码和认证令牌不得上传到 Web 后端、日志、审计记录或用户报表。
12. Web 端能够展示补全中、等待 Seller 登录、自动重试、需要人工补充和补全完成等状态。

## 3. 方案边界

### 3.1 Web 后端负责

- 保存公开采集数据并返回采集成功。
- 创建、去重、租约控制和重试补全任务。
- 合并补全结果并保护用户手动填写的值。
- 记录任务、来源、结果摘要、失败原因和时间。
- 在上架接口执行完整性校验。

### 3.2 扩展负责

- 采集 Ozon 商品页公开数据。
- 观察可信 `seller.ozon.ru` 页面产生的当前 Company ID。
- 使用浏览器内现有 Seller 会话执行只读补全请求。
- 领取 Web 后端创建的补全任务并返回经过白名单投影的数据。
- 显示当前 Seller 识别和恢复状态。

扩展不单独登录 Web、不绑定数据店铺、不发起经营店铺同步、不上传 Seller Cookie。扩展领取补全任务属于只读采集执行，不属于店铺商品、订单、库存等经营数据同步。

### 3.3 不在本次范围

- 自动切换 Seller 店铺。
- 保存 Seller 用户名、密码或验证码。
- 后端直接登录 Seller。
- 使用经营店铺 Client-Id / Api-Key 读取任意竞品 SKU。
- 修改订单、库存、价格或上架行为。

## 4. 总体数据流

1. 扩展从 Ozon 商品页生成公开采集载荷和稳定 `requestId`。
2. Web 后端先按 `accountId + source + sourceSku` 幂等写入采集商品和原始载荷。
3. 若必需字段缺失，商品标记为 `PENDING_ENRICHMENT`，并创建关联的补全任务。
4. 已登录 Web 的扩展 Collector 会话轮询当前账号的补全任务。
5. 扩展解析当前可信 Seller Company ID，并冻结本次执行的上下文版本。
6. 扩展调用 Seller 只读接口，取得目标 SKU 的类目、重量和尺寸。
7. 返回结果前再次核对上下文版本；若店铺已经切换，丢弃结果并重新排队。
8. Web 后端校验任务所有权、结果白名单、SKU 和完整性，然后在事务中合并数据。
9. 合并成功后商品标记为 `COMPLETE`；确认无可用资料时标记为 `NEEDS_ATTENTION`。

## 5. Seller 上下文识别与安全恢复

### 5.1 自动识别

扩展仅接受来自顶层 `https://seller.ozon.ru` 页面的 Company ID。当前实现已能观察 Seller 的 `x-o3-company-id` 请求头，以及精确的 `/api/composer-api.bx/_action/setUserCookies` 请求中名为 `sc_company_id` 的值。本次在此基础上增加上下文版本号和状态通知。

当 Seller 切换店铺产生新的 Company ID 时：

- 保存新的 `companyId`、`observedAt` 和递增的 `revision`；
- 多个 Seller 标签页存在不同历史 Company ID 时，以最近一次可信切换事件作为当前上下文，旧观察值不再制造持续冲突；
- 通知扩展弹窗和 Ozon 商品数据面板刷新显示；
- 中止或作废旧 `revision` 下仍在执行的读取请求；
- 新任务只使用最新上下文。

如果不同 Seller 标签页在短时间内反复产生不同 Company ID，扩展将状态标记为“店铺切换中”，暂停领取新任务，直到最近上下文稳定；不能任意挑选一个店铺继续读取。

### 5.2 恢复顺序

当 Company ID 缺失或过期时，按以下顺序恢复：

1. 查询现有 Seller 页面中的主世界观察器，不刷新页面。
2. 如果仍无法识别，复用扩展自己创建且未被用户使用的恢复页。
3. 如果没有恢复页，创建一个非激活的 Seller 恢复页。
4. 识别成功后关闭扩展自己创建的恢复页；不得关闭用户页面。
5. 如果恢复页进入登录页面，停止自动重载，显示“需要登录 Seller”。用户登录成功后自动继续。

无论何种情况，都不得自动刷新正在编辑商品、填写表单或处于激活状态的用户 Seller 页面。

## 6. 状态和失败处理

商品补全状态：

- `PENDING_ENRICHMENT`：已采集公开数据，等待补全。
- `WAITING_FOR_SELLER`：缺少有效 Seller 登录状态。
- `RETRYING`：Ozon 或网络临时失败，等待下次重试。
- `COMPLETE`：必需字段完整。
- `NEEDS_ATTENTION`：确认无资料、格式不合法或达到自动重试上限，需要人工填写。

任务继续使用数据库租约防止重复执行。可重试失败采用逐步延长间隔，例如 30 秒、2 分钟、10 分钟、30 分钟，之后最高每小时一次。登录缺失和扩展离线不视为商品永久失败。任务重新领取时必须验证原租约已经失效，避免重复副作用。

## 7. 数据合并规则

- 公开采集载荷先保存为原始证据，不因补全失败而丢失。
- 补全数据写入同一采集商品，不新建第二份商品。
- 只填充空值；用户手动填写的非空值优先。
- 包装重量统一归一为克，包装长宽高统一归一为毫米，同时保留原始响应摘要和采集时间。
- Ozon `description_category_id` 作为来源类目证据保存，不直接等同于目标经营店铺上架类目。
- 目标店铺类目匹配仍在上架准备阶段按用户选择的经营店铺执行。
- 合并必须使用版本检查或等价的事务保护，避免后台补全覆盖用户同时进行的编辑。

## 8. Contract 与数据持久化

### 8.1 采集接口

现有同步“必须完整才写入”的行为调整为：

- 公开字段合法即可创建采集商品；
- 响应返回商品 ID、补全状态和缺失字段；
- 完整数据仍可直接标记为 `COMPLETE`；
- `requestId` 和账号级 SKU 身份规则保持不变。

### 8.2 补全结果接口

结果载荷分为两部分：

- `variantData`：经过白名单限制的商品数据；
- `captureContext`：Company ID、上下文 revision 和观察时间。

后端只接受任务所属 Collector 会话的结果。Company ID 仅进入内部来源记录和审计，不进入前端公开商品结构。Seller Cookie 不属于接口 contract。

### 8.3 数据库

复用现有 `collect_items`、`collect_raw_payloads`、`collect_requests`、`collector_ozon_enrichment_cache` 和 `collector_ozon_enrichment_jobs`。通过新的向后兼容迁移补充任务与采集商品关联、重试时间、尝试次数和来源上下文所需字段。只新增可空字段或安全默认值，不删除旧列，不重写已有数据。

## 9. 页面和交互

### 9.1 扩展弹窗与商品数据面板

显示以下状态之一：

- `Seller 已识别 · Company ID …`
- `正在识别 Seller 店铺`
- `需要登录 Seller`，并提供“打开 Seller 登录”按钮
- `Seller 店铺已切换`

能可靠取得店铺名称时显示“店铺名称 + Company ID”；否则只显示 Company ID，不猜测名称。

### 9.2 Web 采集箱

采集成功提示改为“已加入采集箱，资料正在后台补全”。采集箱和编辑页显示缺失字段与补全状态，并提供人工重试入口。`WAITING_FOR_SELLER` 状态说明需要在安装扩展的同一浏览器登录 Seller。

### 9.3 上架门禁

前端按钮状态只用于提示。真正的类目、包装重量、包装长宽高完整性检查必须保留在后端上架接口；缺失时返回稳定错误码和缺失字段列表。

## 10. 权限、隔离和可追溯性

- 所有采集商品、补全任务、缓存和查询按服务端认证得到的 `accountId` 隔离。
- 客户端不得提交或覆盖 `accountId`、经营店铺 ID 或历史数据店铺字段。
- Collector 会话只能领取自己账号的只读补全任务。
- 任务结果记录 request ID、SKU、Collector 会话 ID、Company ID、采集时间、响应哈希、状态和稳定错误码。
- 日志和审计严禁记录 Cookie 值、认证令牌、密码、验证码或完整敏感响应。
- Seller 外部调用只执行读取；本次不增加价格、库存、订单或上架写操作。

## 11. 影响范围

- 扩展：Seller 上下文观察与恢复、补全代理、弹窗、Ozon 商品数据面板、扩展打包版本。
- Web 前端：采集箱状态、编辑页缺失字段和重试提示。
- Web 后端：采集写入顺序、补全任务服务、结果合并、上架完整性门禁、审计。
- 数据库：兼容性新增迁移。
- 外部服务：`seller.ozon.ru` 只读接口；无新增第三方服务和密钥。

## 12. 测试与回归

### 12.1 自动测试

- Seller Company ID 来源域名、顶层页面和格式校验。
- Seller 店铺切换后 revision 更新，旧请求结果被拒绝。
- 不刷新或关闭用户 Seller 页面，只管理扩展恢复页。
- 缺少 Seller 登录时任务保持可恢复。
- 公开数据先入箱、任务幂等、租约重领和重试退避。
- 补全合并不覆盖用户编辑值。
- 多账号任务、缓存和商品严格隔离。
- 结果 contract 拒绝多余字段、伪造账号和敏感信息。
- 上架接口后端完整性门禁。
- 旧的完整采集请求继续正常工作。

### 12.2 浏览器回归

1. Seller 已登录，采集一个缺少尺寸的 Ozon 商品，确认先入箱后自动补全。
2. Seller 未登录时采集，确认商品保留；登录后自动继续。
3. 在 Seller 切换店铺，确认扩展状态自动变化且无需手动刷新。
4. Seller 编辑页存在未保存输入时触发恢复，确认页面不刷新。
5. 补全期间手动填写重量，确认后台结果不覆盖该值。
6. 扩展离线后恢复，确认任务继续且不产生重复商品。

### 12.3 未验证范围

真实 Ozon 接口可能调整内部路径或响应结构。实现阶段需要在授权的 Seller 测试账号中验证当前接口，并将结构变化收敛在适配器和稳定错误码内，不能把猜测固化为业务规则。

## 13. 发布与回滚

- 先部署兼容性数据库迁移和后端，再发布 Web 前端，最后发布扩展。
- 新后端在旧扩展尚未升级时应保持可用：任务等待而不是破坏采集数据。
- 回滚时恢复上一版扩展、Web 和服务端代码；新增数据库字段保留不用，不做破坏性回滚。
- 如果 Seller 内部接口发生变化，暂停补全执行并保留待处理任务；公开数据采集和人工编辑仍可使用。
