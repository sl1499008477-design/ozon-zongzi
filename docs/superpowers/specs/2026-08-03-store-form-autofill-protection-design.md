# 新增门店表单防登录凭据自动填充设计

## 背景与根因

“新增 API 授权门店”弹窗的应用初始值已经为空，但浏览器看到相邻的普通文本框和密码框后，会把它们误判为登录账号与密码字段，从密码管理器中自动填入 Web 登录用户名和密码。截图中的 `admin` 与圆点密码属于浏览器自动填充，不是门店数据、接口响应或数据库默认值。

## 业务目标与验收标准

- 打开新增门店弹窗时，Client-Id、Api-Key 和标签保持为空。
- 浏览器不得把已保存的 Web 登录账号和密码填入 Client-Id、Api-Key。
- API Key 创建日期仍默认采用新增门店当天。
- 修改门店时仍显示原 Client-Id，Api-Key 仍保持空白，用户不填写时不修改已保存密钥。
- 15 秒后台状态刷新不得覆盖用户正在输入的内容。
- 不改变门店保存接口、数据结构、权限校验和数据库数据。

## 方案

采用标准 HTML 自动填充语义，保持现有表单交互：

- 门店表单声明关闭通用自动填充。
- Client-Id 声明为非登录凭据字段，避免被当作用户名。
- Api-Key 声明为新密钥字段，避免密码管理器填入已保存的 Web 登录密码。
- 标签和日期保持现有业务行为。
- 不采用“初始只读、点击后解锁”的额外状态方案，避免键盘操作和可访问性退化。

## 影响范围与 Contract

- 页面：门店配置页的新增/修改 API 授权门店弹窗。
- 前端：只调整输入框的浏览器自动填充元数据。
- API：无变化。
- 数据库：无变化、无迁移。
- 权限与多店铺边界：无变化。
- 外部服务与真实 Ozon 调用：无变化。

## 测试与验证

- 先扩展现有真实浏览器回归测试，断言表单及 Client-Id、Api-Key 的自动填充语义；修改生产代码前确认测试因缺少这些标记而失败。
- 实现最小前端修改后重新运行该测试，确认新增、修改及 15 秒刷新行为全部通过。
- 运行前端构建和项目验证。
- 在本地实际门店页面打开弹窗，确认登录账号密码不会再写入两个门店字段，且测试过程不提交表单。

## 失败处理、回滚与风险

- 若特定密码管理器仍忽略标准语义，再单独评估“初始只读、聚焦解锁”作为兼容兜底，不在本次提前引入。
- 本次修改仅涉及 HTML 表单元数据，出现问题时可回退对应前端提交；不需要恢复数据库。
- 主要回归风险是修改门店时的字段展示或 Api-Key 留空语义被破坏，由现有浏览器回归测试覆盖。
