# 自动上架店铺原币支持设计

## 背景与目标

当前自动上架链路把来源价格证据、定价计算、冻结商品底稿、Ozon 提交和页面文案都固定为 `RUB`。这会把合法的人民币店铺挡在任务创建阶段，也会诱使操作者把人民币金额错误地改标为卢布。

本次目标是让自动上架严格跟随目标店铺币种，第一阶段只支持已经明确验收的 `RUB` 和 `CNY`：

- `RUB` 店铺继续使用现有卢布规则，历史任务与历史证据保持可读、可执行。
- `CNY` 店铺以人民币原币计算，阈值为 `80 CNY`，调整金额以人民币填写，最终向 Ozon 提交 `CNY`。
- 不执行 CNY/RUB 汇率换算，不把金额仅通过替换币种代码来转换。
- 其他币种继续失败关闭，后续必须有独立业务依据和验收后才能增加。

## 业务规则

### 店铺币种是最终权威

任务创建时，后端在租户边界内读取目标店铺，并冻结其币种。只接受 `RUB` 或 `CNY`。

来源商品明确提供币种时：

- 来源币种必须是 `RUB` 或 `CNY`；
- 来源币种必须与目标店铺币种一致；
- 不一致时该商品进入可解释的阻止状态，不创建 AI 任务，也不产生 Ozon 写入。

来源商品没有币种时，只在以下条件同时成立时采用目标店铺币种：

- 来源商品已经持久化了明确的目标店铺类目证据；
- 该证据中的店铺 ID 与本次目标店铺完全一致；
- 目标店铺币种是 `RUB` 或 `CNY`。

价格证据必须记录币种来源：

- `SOURCE`：来源商品明确携带并通过匹配验证；
- `TARGET_STORE`：来源缺失币种，依据完全匹配的目标店铺证据补全。

任何显式币种冲突都不得被目标店铺币种覆盖。

### 原币金额计算

价格计算继续使用整数最小货币单位：

- `RUB` 使用戈比；
- `CNY` 使用分；
- 两者都是 100 个最小单位等于 1 个主币单位。

为保持数据库与请求 contract 的向后兼容，现有内部字段 `blackKopecks`、`greenKopecks`、`adjustmentKopecks` 和 `finalPriceKopecks` 暂不改名；在新版 contract 中它们统一解释为“当前币种的最小单位”，不再解释为只能是戈比。

两种币种采用相同的已确认公式，但所有数字都处于各自原币中：

- 黑标价大于等于 80 个主币单位：`真实售价 =（黑标价 - 绿标价）× 2.25 + 黑标价`；
- 黑标价低于 80 个主币单位：`真实售价 = 黑标价 ÷ 1.0715`；
- `最终售价 = 真实售价 + 调整金额`。

计算过程继续使用整数和有明确名称的四舍五入规则，不使用浮点金额。

### 店铺切换

自动上架页面根据所选店铺显示：

- `CNY`：`售价加减（人民币）`，金额符号使用 `¥`；
- `RUB`：`售价加减（卢布）`，金额符号使用 `₽`。

当用户从一种币种的店铺切换到另一种币种的店铺时，页面把调整金额重置为 `0`，并显示说明，避免把原币调整金额带到另一币种。

同币种店铺之间切换不需要重置。

## 稳定 contract

### 来源快照价格证据 V2

新任务的价格证据增加币种来源：

```json
{
  "currency": "CNY",
  "currencySource": "TARGET_STORE",
  "blackKopecks": "10000",
  "greenKopecks": "8000"
}
```

允许值：

- `currency`: `RUB | CNY`
- `currencySource`: `SOURCE | TARGET_STORE`

旧 RUB 来源快照继续按旧结构校验和读取，不做数据重写。

### 冻结商品底稿

新增 `AUTO_LISTING_LISTING_BASE_V2`：

- 支持 `RUB` 和 `CNY`；
- 价格证据包含 `currencySource`；
- 每个 Ozon 商品项的 `currency_code` 必须等于价格证据币种；
- 价格证据币种必须等于冻结目标店铺币种；
- canonical hash 覆盖币种和币种来源。

`AUTO_LISTING_LISTING_BASE_V1` 仍只接受现有 RUB 结构。历史 V1 行不更新、不重算 hash。

### Ozon 提交

上传前必须同时核对：

- 冻结商品底稿币种；
- 当前任务冻结的目标店铺币种；
- 每个提交商品的 `currency_code`。

三者必须完全一致。任何不一致都在网络调用前失败，不发送商品、不修改库存。

### 安全错误码

新增或替换为币种中立的稳定错误：

- `AUTO_LISTING_SOURCE_CURRENCY_UNSUPPORTED`
- `AUTO_LISTING_SOURCE_CURRENCY_MISMATCH`
- `AUTO_LISTING_TARGET_STORE_CURRENCY_UNSUPPORTED`
- `PRICE_CURRENCY_UNSUPPORTED`

历史 `AUTO_LISTING_SOURCE_CURRENCY_NOT_RUB` 只用于读取已有阻止记录；新任务不再生成该错误码。

前端只显示固定中文文案，不透传后端原始消息或 Ozon 响应。

## 数据库迁移

新增 forward-only 迁移 `062_auto_listing_store_currency.sql`：

- 不更新历史数据；
- 保留 V1/RUB 约束；
- 为新插入的 V2 允许 `RUB | CNY`，并要求合法 `currencySource`；
- 重装完整性触发器，使 V1 与 V2 按各自 contract 校验；
- 约束 V2 的价格证据、冻结变体币种和目标店铺币种一致；
- 迁移采用先添加/验证新约束、再替换旧约束的向前兼容方式；
- 不删除或放宽租户、不可变、审计、幂等和外部写安全约束。

如果回滚应用代码，历史 V1 继续可用；迁移 062 不应删除。要停止 CNY 新任务，应通过应用开关拒绝新建，而不是删除 V2 数据或逆向修改迁移。

## 数据流

1. 页面选择目标店铺并读取其公开币种投影。
2. 页面显示对应原币调整字段；跨币种切换时重置调整值。
3. 后端读取并锁定同租户目标店铺与仓库证据。
4. 后端用来源显式币种或严格受限的目标店铺回退生成 V2 来源价格证据。
5. 定价模块按该币种的整数最小单位计算。
6. 冻结底稿 V2 绑定目标店铺、币种、币种来源、计算证据和 canonical hash。
7. 上传覆盖层生成相同币种的 Ozon 商品项。
8. 网络调用前再次验证任务、底稿、店铺和商品项币种一致。
9. 审计和安全 DTO 返回币种，不返回凭据或原始外部响应。

## 测试与验收

### 单元合同

- CNY 的 79.99、80.00、高分支、低分支、正负调整和四舍五入。
- RUB 所有现有算价用例保持不变。
- USD 等未支持币种失败关闭。
- 来源显式 CNY + CNY 店铺通过。
- 来源显式 RUB + CNY 店铺以 mismatch 阻止。
- 来源缺失币种 + 精确目标店铺证据采用 `TARGET_STORE`。
- 来源缺失币种 + 店铺证据缺失或错配失败关闭。
- 页面显示正确币种名称和符号；跨币种切换清零，同币种切换保留。

### 数据库与集成

- 从 001 到 062 在全新 PostgreSQL 临时库迁移成功。
- 历史 V1/RUB 行在 062 后仍可读取和执行。
- V2/CNY 行可插入并保持 append-only。
- V1/CNY、V2/USD、币种来源非法、店铺/证据/变体币种错配均由数据库拒绝。
- CNY 自动上架完整链路使用真实 repository/service/worker 和 loopback fake Ozon，断言最终 `/v3/product/import` 的 `currency_code` 为 `CNY`。
- 失败路径断言 AI outbox、Ozon 商品写和库存写均为 0。
- 现有 RUB、RFBS、幂等、重试、租户隔离和 worker 写前门禁回归通过。

### 手工验收

- “粽子测试”店铺显示 `售价加减（人民币）`。
- 当前采集商品币种为空但类目目标店铺精确匹配时，可以创建 CNY 任务。
- 任务详情和冻结价格显示 `CNY`，不会出现 RUB 或卢布文案。
- 未授权真实 Ozon 前只运行 fake Ozon 验证，不产生真实外部写入。

## 非目标

- 不支持 USD、EUR、KZT、BYN 等其他币种。
- 不引入实时或手工汇率换算。
- 不改变店铺本身的币种配置。
- 不修改历史 RUB 快照、价格证据、底稿或审计记录。
- 不借本次改动重构 AI、仓库验证、上传重试或其他无关流程。

## 可观测性与恢复

- 任务、价格证据和底稿安全 DTO 中保留币种与币种来源。
- 币种错误使用固定错误码并带现有 correlation ID，日志不得记录密钥或原始 Ozon 响应。
- 创建任务和上传继续保持幂等；相同幂等键不得因为币种支持而产生第二份任务或第二次外部写入。
- 发现 CNY 规则异常时，可关闭 CNY 新任务；已有 V1/RUB 不受影响，V2 数据保留供审计与恢复。
