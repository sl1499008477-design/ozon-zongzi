# 新增门店表单与后台刷新隔离设计

## 问题

经营店铺页面每 15 秒刷新一次本地状态。刷新会生成新的当前门店对象，而门店弹窗的表单初始化逻辑监听了该对象。弹窗保持打开时，后台刷新再次调用 `setFieldsValue`，导致用户正在输入的 Client-Id、Api-Key、标签和创建日期被当前门店数据覆盖。

## 已确认方案

采用“打开时初始化一次”的方案：

- 新增门店：Client-Id、Api-Key、标签为空，API Key 创建日期默认为当天。
- 修改门店：打开时读取一次所选门店的 Client-Id、标签和创建日期，Api-Key 保持为空。
- 弹窗打开后，后台状态刷新不得改写任何表单字段。
- 关闭后重新打开弹窗时，重新按新增或修改模式初始化。
- 保留现有 15 秒后台刷新，不暂停、不改变刷新范围和接口。

## 实现边界

表单初始值由“打开弹窗”这一明确事件负责。后台 `binding` 状态变化只更新页面店铺信息，不再承担已打开表单的初始化职责。保存接口、门店数据结构、权限、密钥处理、有效期计算和后端接口均不改变。

## 验收标准

1. 新增弹窗首次打开时三个文本字段为空，日期为当天。
2. 用户输入内容后，即使本地状态再次刷新，四个字段仍保持用户输入。
3. 修改弹窗首次打开时显示所选门店数据；之后后台刷新不覆盖用户修改。
4. 关闭并重新打开时，不保留上一次未提交的内容。
5. 新增和修改门店的既有提交行为、校验与 Api-Key 不回显规则保持不变。

## 测试策略

新增一个以真实 React 页面为对象的浏览器回归测试：打开新增弹窗、输入测试内容、触发一次新的本地状态响应，断言输入值不变；关闭再打开，断言恢复新增默认值。相关 App 测试与构建继续作为回归门禁。

## 风险与回滚

风险集中在弹窗初始化时机：如果初始化遗漏，修改弹窗可能显示旧值或空值。测试同时覆盖新增、修改和重新打开以控制该风险。出现问题时可单独回滚本次表单初始化提交，不涉及数据库迁移或数据恢复。
