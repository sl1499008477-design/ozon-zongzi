# Seller 商品包缓存补全设计

## 目标

用户从 Ozon 数据面板采集商品后，若面板已经通过当前 Seller 店铺取得完整商品包，后台补全应直接复用该只读缓存，使产品类目、包装重量、包装长宽高进入采集箱，不再因公开页面取数失败而持续重试。

## 当前问题

数据面板的普通查询会调用 Seller `/search`，并通过 bundle 接口取得完整商品包后写入按 `companyId + variantId` 隔离的本地缓存。异步补全为了避免创建 Seller 草稿，使用 `readOnly` 路线，但该路线完全跳过已有 bundle 缓存，只尝试从 Ozon 公开页面补物理字段。公开页面取数失败时，完整缓存虽然存在，补全任务仍会报告缺少类目、重量和尺寸。

## 方案

在 `readOnly` 补全路线中增加“只读缓存命中”步骤：

1. 使用当前已确认的 Seller `companyId` 和 `/search` 返回的 `variantId` 生成现有缓存键。
2. 只读取未过期且包含有效属性的 bundle 缓存，不调用会创建草稿的 bundle 接口。
3. 命中后使用现有合并函数把类目、重量、长宽高及属性合并进 Seller 搜索结果。
4. 合并后若五项必需数据仍不完整，再执行现有公开页面物理字段兜底。
5. 缓存按 Seller 公司隔离；不接受其他公司、过期、空属性或损坏的缓存。

## Contract 与安全边界

- 不修改采集上传接口、补全结果接口或数据库结构。
- 不把 Seller 凭据、Cookie、店铺编号写入采集 payload。
- 不在 `readOnly` 路线调用有副作用的 bundle 创建接口。
- 继续由现有投影与敏感字段校验决定哪些商品字段可以提交到 Web 后端。

## 失败处理

- 缓存读取异常视为未命中，不阻断后续公开页面兜底。
- 缓存不完整时保持现有重试状态和错误码。
- 不改变任务幂等键、重试次数或账号边界。

## 验收与测试

- 已有同店铺完整 bundle 缓存时，`readOnly` 补全返回完整类目和物理字段。
- 命中缓存时不会调用公开页面取数，也不会调用 bundle 创建接口。
- 其他店铺缓存、过期缓存和空属性缓存不被复用。
- 缓存不完整时仍调用现有公开页面兜底。
- 扩展补全客户端、Agent、采集协调器及相关安全测试保持通过。

## 回滚

删除新增的只读缓存读取逻辑即可恢复原有公开页面兜底路线；无需回滚数据库或清理已采集数据。
