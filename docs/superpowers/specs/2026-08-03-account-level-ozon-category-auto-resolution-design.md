# 采集成功后自动匹配 Ozon 当前类目设计

## 1. 背景

当前采集流程会把商品先写入账号级统一采集箱，并保存 Ozon 商品原有的类目证据。目标上架类目的自动匹配目前发生在用户进入采集箱编辑页之后，因此每个商品都需要至少打开一次“查看”页面，才能得到可用于上架的 `description_category_id` 与 `type_id`。

实际商品 `collect_01f58aaf31bf8bdc28434a29` 证明来源类目和当前可上架类目可能不同：

- 采集来源：`description_category_id = 17033604`、`type_id = 94405`；
- Ozon 当前类目树：`description_category_id = 17028702`、`type_id = 94405`；
- 商品类型没有改变，变化的是 Ozon 类目树中的归属节点。

类目树属于 Ozon 分类体系，不应在没有平台依据的情况下被建模成某个经营店铺私有的数据。经营店铺的凭据用于读取和验证 Ozon 当前类目树；当多个经营店铺使用同一 Ozon 类目体系时，已经核验的结果应当共享。

## 2. 业务目标

1. 商品成功进入采集箱并完成资料补全后，由 Web 后端自动匹配 Ozon 当前有效类目，不再要求用户逐个打开“查看”页面。
2. 保留采集来源类目作为不可丢失的来源证据；自动匹配结果作为当前可上架类目单独保存。
3. 使用采集请求被后端接受时的当前经营店铺作为首次查询凭据来源，但不把采集商品永久绑定到该店铺。
4. 同一 Ozon 类目体系下切换经营店铺时复用已匹配结果，只做有效性检查；验证失败或类目树发生变化时才重新匹配。
5. 类目匹配失败不能把已经成功的商品采集改成失败状态；商品应进入可恢复的“类目待处理”状态。

## 3. 非目标

- 插件不负责类目匹配，也不发送类目匹配指令。
- 插件采集合同不新增经营店铺 ID，继续保持账号级采集边界。
- 不把采集记录的 `store_id` 恢复为必填字段。
- 不根据中文或俄文名称直接认定类目相同；名称只用于展示和无 ID 时的人工辅助。
- 不在类目结果仍有效时因切换经营店铺重复执行完整匹配。
- 不自动上架、保存用户文案修改或产生其他 Ozon 写操作。

## 4. 术语与判断依据

### 4.1 采集来源类目

采集或 Seller 补全阶段取得的原商品分类证据，包括：

- `descriptionCategoryId`
- `typeIdCandidate`
- `typeName`
- 原始类目路径
- 原始属性及字典值 ID
- 采集来源、原始响应引用和采集时间

来源类目只增补缺失证据，不被目标匹配结果覆盖。

### 4.2 Ozon 当前类目匹配结果

从 Ozon 当前可用类目树中核验得到的上架组合，包括：

- `descriptionCategoryId`
- `typeId`
- 中文、俄文展示路径
- 匹配方法
- 类目树指纹
- 首次匹配凭据店铺 ID
- 核验时间

该结果的共享边界是“账号 + Ozon 类目体系 + 商品类型 + 类目树指纹”，不是单个经营店铺。

### 4.3 类目体系标识

系统必须使用明确且稳定的 `taxonomyScope` 区分类目体系。当前只接入一个 Ozon 类目体系时可以使用固定值；未来如果接入不同国家站点、合同体系或 Ozon 明确返回不同类目树，必须使用不同的 `taxonomyScope`。

语言不属于不同类目体系。中文和俄文树的 ID 结构相同时，它们只是同一结果的不同展示名称。

Ozon 没有提供可用的类目树版本号时，`taxonomyFingerprint` 由后端对规范化后的启用节点结构计算哈希。哈希输入只包含排序后的 `description_category_id`、`type_id`、父子关系和启用状态，不包含中俄文名称，因此切换展示语言不会误判为类目树变化。

## 5. 推荐流程

### 5.1 采集请求被接受

1. 插件按现有账号级 Collector contract 上传商品，不携带经营店铺信息。
2. Web 后端完成账号权限校验、幂等去重和商品写入。
3. 后端读取该账号在这一时刻选中的当前经营店铺，并冻结为本次自动匹配的 `credentialStoreId`。
4. `credentialStoreId` 只记录“使用哪个店铺凭据查询”，不得写回采集商品的店铺归属字段。
5. 如果没有当前店铺或店铺没有可用凭据，采集仍然成功，类目状态记为“等待可用店铺”。

### 5.2 资料补全完成

1. 商品来源类目、重量、尺寸等资料达到补全完成状态后，后端创建或唤醒类目匹配任务。
2. 类目任务使用冻结的 `credentialStoreId` 查询 Ozon 当前类目树。
3. 优先按 Ozon `type_id` 精确匹配，不以中俄文名称差异作为失败依据。
4. 只有一个启用的叶级类目包含该 `type_id` 时，保存当前类目匹配结果。
5. 找不到结果、找到多个结果或 Ozon 数据不可用时，保存稳定失败原因并进入可重试状态。

### 5.3 切换经营店铺

1. 用户选择另一个目标经营店铺时，先读取账号级共享类目结果。
2. 如果新店铺属于相同 `taxonomyScope`，且当前类目树指纹未变化，直接复用结果，不重新匹配。
3. 如果无法确认树指纹一致，使用新店铺凭据执行轻量有效性检查：目标类目启用、目标类型仍位于该类目下、属性接口可以读取。
4. 有效性检查通过后继续复用原结果，只追加核验记录。
5. 检查失败、目标节点停用、类型迁移或类目树指纹变化时，才触发完整重新匹配。

### 5.4 打开采集箱编辑页

1. 页面优先读取后端已保存的共享类目结果。
2. 匹配已完成时直接显示“类目已匹配”，不再自动重复调用预览匹配接口。
3. 类目匹配仍在进行时显示“后台匹配中”。
4. 类目待人工处理时保留手动选择能力。
5. 用户手动选择的结果必须标记为 `MANUAL`，并具有高于自动结果的优先级；除非用户清除或目标已失效，后台任务不得覆盖。

## 6. 状态模型

类目自动匹配状态采用闭环状态：

- `WAITING_ENRICHMENT`：等待来源资料补全。
- `WAITING_STORE`：没有可用的经营店铺凭据。
- `QUEUED`：已进入匹配队列。
- `MATCHING`：正在读取或核验类目树。
- `MATCHED`：已得到唯一且有效的当前类目组合。
- `NEEDS_REVIEW`：缺少来源类型、结果不唯一或需要人工选择。
- `RETRYABLE_ERROR`：网络、限流或 Ozon 临时错误，可自动重试。
- `INVALIDATED`：原结果因类目树变化、节点停用或验证失败而失效，等待重新匹配。

不允许从终态任意跳转。`MATCHED` 只能因明确的树版本变化、有效性检查失败或用户手动清除进入 `INVALIDATED`。

## 7. 数据与合同

### 7.1 来源证据

继续使用现有 `sourceCategory` contract，保持与目标结果分离，并保存来源原始响应引用或哈希，满足数据追溯要求。

### 7.2 共享类目结果

新增独立的账号级类目解析记录，至少包含：

- `accountId`
- `collectItemId`
- `taxonomyScope`
- `sourceTypeId`
- `targetDescriptionCategoryId`
- `targetTypeId`
- `method`
- `status`
- `taxonomyFingerprint`
- `credentialStoreId`
- `matchedAt`
- `validatedAt`
- `failureCode`
- `failureDetailSafe`

不得把店铺密钥、访问令牌、Cookie 或原始敏感响应写入记录或日志。

### 7.3 幂等键

自动匹配任务使用稳定幂等键：

`accountId + collectItemId + taxonomyScope + sourceTypeId + taxonomyFingerprint`

重复采集、重复补全完成通知、服务重启和人工重试不得创建重复结果或重复外部调用副作用。

### 7.4 对外读取合同

采集箱返回稳定的类目状态摘要，但不直接暴露数据库结构。摘要至少包含：

- `status`
- `targetDescriptionCategoryId`
- `targetTypeId`
- `displayPath`
- `matchedAt`
- `validatedAt`
- `action`
- 稳定中文提示

## 8. 失败与恢复

- 没有店铺：保持 `WAITING_STORE`；店铺绑定或恢复凭据后自动唤醒。
- 资料未完成：保持 `WAITING_ENRICHMENT`；补全完成事件自动唤醒。
- Ozon 限流或网络错误：指数退避并限制最大重试频率。
- 类目树不可用：保持已有有效结果，不用空响应覆盖；标记核验延期。
- 类型不存在：进入 `NEEDS_REVIEW`，不猜测固定类目。
- 多个候选：进入 `NEEDS_REVIEW`，展示候选供人工选择。
- 类目失效：原结果进入 `INVALIDATED`，保留历史记录并重新匹配。
- 手动结果失效：提示用户重新选择，不由后台静默改成其他类目。

## 9. 权限、边界与审计

- 所有类目任务由后端按 `accountId` 校验数据边界。
- `credentialStoreId` 必须属于同一账号、处于启用状态且具有可用凭据。
- 店铺切换不能访问其他账号的类目缓存、任务或匹配结果。
- 记录任务创建原因、使用的类目树指纹、匹配依据、凭据店铺、结果、重试次数和时间。
- 日志只记录稳定 ID 与错误码，敏感凭据继续走现有密钥管理。

## 10. 页面表现

采集箱中的商品显示以下状态之一：

- `类目匹配中`
- `类目已匹配`
- `等待选择经营店铺`
- `等待商品资料补全`
- `需要人工选择类目`
- `类目匹配暂时失败，系统将自动重试`

“查看”按钮只用于查看和编辑，不再承担触发自动匹配的职责。

## 11. 验收标准

1. 有当前有效店铺的账号采集商品后，不打开编辑页也能自动得到目标类目。
2. 来源 `17033604 / 94405` 可以自动解析为当前 `17028702 / 94405`。
3. 来源类目仍完整保留，目标结果不能覆盖来源证据。
4. 店铺 A 完成匹配后切换同类目体系的店铺 B，直接复用结果，不执行完整匹配。
5. 类目树发生变化或 B 验证失败时才重新匹配。
6. 中文和俄文名称不同但 ID 相同时仍判定为同一结果。
7. 没有店铺、凭据失效、网络失败或匹配不唯一时，商品采集仍保持成功。
8. 重复通知和重复重试不产生重复记录。
9. 人工选择结果不会被后台自动任务静默覆盖。
10. 打开已匹配商品的编辑页不再发起重复匹配请求。

## 12. 测试范围

- 账号级类目结果共享及多账号隔离测试。
- 采集成功后自动排队和补全完成后唤醒测试。
- `type_id` 精确匹配、名称跨语言不参与覆盖判断测试。
- 店铺 A 到店铺 B 的复用、轻量验证及失效重匹配测试。
- 类目树空响应、旧响应、节点停用和多候选测试。
- 幂等、并发、重复通知、服务重启恢复测试。
- 人工结果优先级测试。
- 采集箱状态显示和编辑页不重复匹配回归测试。
- 上架预检继续使用当前有效 `description_category_id + type_id` 的合同测试。

## 13. 兼容、迁移与回滚

- 现有只有 `sourceCategory` 的采集记录保持可读，后台按需补建类目任务。
- 现有按店铺保存且仍有效的 `categoryResolution` 可迁移为共享结果，同时保留原记录作为审计历史。
- 数据库变更只新增记录或字段，不删除旧数据。
- 上线时先启用只读共享结果与状态展示，再启用后台自动任务。
- 回滚时停止创建新任务并恢复编辑页按需匹配；已保存的来源证据和匹配结果保留，不做破坏性删除。

## 14. 最终业务规则

采集商品继续属于账号级统一采集箱。采集成功后，Web 后端使用当时选中的有效经营店铺作为查询凭据，在资料补全完成后自动获取并匹配 Ozon 当前类目。匹配结果默认在同一账号、同一 Ozon 类目体系和同一类目树版本内共享；更换经营店铺时优先复用并做有效性检查，只有失效或类目体系不同才重新匹配。
