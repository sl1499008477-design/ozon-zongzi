# Sonli 基线稳定与安全改造设计

日期：2026-07-28
状态：已确认
目标分支：`codex/baseline-stabilization`

## 1. 目标

把当前包含大量未提交成果的工作区整理为可审查、可验证、可回滚的工程基线，并在此基础上逐步修复以下风险：

- 巨型入口和脚本导致的跨功能耦合。
- 普通业务路由未统一使用 `tenant.operate` 权限门禁。
- Service 仍可隐式读取全局当前账号或店铺。
- 上架链路存在未绑定业务依据的价格、VAT、币种和尺寸默认值。
- 根验证命令未完整覆盖前端、服务端、扩展、桌面端和 PostgreSQL 集成测试。
- 关键 API 依赖松散约定，缺少独立、稳定、可测试的 contract。

本设计不承诺任何修改对其他功能绝对零影响。目标是让影响范围可识别、非预期回归可检测、失败可恢复、外部副作用可控制。

## 2. 全局约束

- 保留当前所有来源未确认的文件，不以清理为名直接删除。
- 基线阶段只整理文件归属、依赖和验证环境，不改变业务行为。
- 一个 Service 只处理一个明确业务用例。
- 业务模块通过稳定 contract、Port、任务 ID 或明确接口协作。
- 权限和租户范围必须由后端校验，不能只依赖前端显隐。
- 账号、店铺、任务、缓存、导入、导出和外部调用必须带明确数据范围。
- 金额使用最小货币单位并携带币种。
- 外部调用和任务执行必须幂等；未知结果进入对账或恢复流程。
- 真实 Ozon 写操作、真实店铺同步、生产迁移和密钥变更不属于普通验证范围，执行前必须单独确认。
- 每个改造包必须能够独立测试、审查和回退。

## 3. 非目标

- 不进行一次性全项目重写。
- 不在基线提交中顺手修改业务规则。
- 不把现有前端、扩展或桌面端整体迁移到新的技术栈。
- 不直接删除现有数据库表、字段或业务数据。
- 不通过重新提交外部请求来伪造回滚。
- 不把当前旧代码中的平台参数视为已确认的 Ozon 规则。

## 4. 保护性基线

### 4.1 分支

所有基线整理工作位于 `codex/baseline-stabilization`。现有工作区改动继续保留，不通过 `reset --hard`、强制检出或批量删除恢复干净状态。

### 4.2 文件分类

每个未跟踪文件必须属于以下一种类型：

1. 源代码
2. 自动测试
3. 数据库迁移
4. 配置或部署
5. 架构、设计或交付文档
6. 可重复生成的产物
7. 来源待确认的运行资产

不能确认来源或重建方式的文件按“来源待确认的运行资产”保留。

### 4.3 分类提交顺序

保护性基线按以下顺序提交：

1. 基础设施与 workspace 配置
2. 服务端业务模块与数据库迁移
3. 前端页面和共享模块
4. 浏览器扩展源代码
5. 桌面端运行代码和资源
6. 测试、验证和安全门禁
7. 架构、设计和交付文档
8. 暂时必须保留的生成产物或运行资产

每次提交只包含一个类别。提交前运行该类别当前可用的静态检查和测试；环境原因造成的失败必须记录，不能标记为通过。

### 4.4 基线清单

基线完成时必须记录：

- 每个分类提交的文件范围。
- 可生成产物及其重建命令。
- 来源待确认资产及其消费者。
- 当前通过、失败和未运行的测试。
- 数据库、对象存储和外部服务依赖。
- 恢复到基线的提交和操作说明。

## 5. 稳定基线门禁

### 5.1 统一依赖管理

根 workspace 必须显式包含实际子包，至少覆盖：

- Web 应用
- 桌面应用
- 根服务端与脚本

从干净检出开始，一次文档化的依赖安装流程必须能够准备完整验证环境。各子包不得依赖开发者机器上未声明的全局包。

### 5.2 根验证命令

根 `pnpm verify` 必须覆盖：

- Web 构建与测试
- 服务端语法和单元测试
- PostgreSQL 集成测试
- 数据库迁移并发与重复执行测试
- 扩展源码、压缩包一致性和 smoke 测试
- 桌面端语法、contract 和单元测试
- Docker Compose 配置检查
- 敏感信息字面量和日志扫描
- 工作区差异格式检查

任一必需检查失败时，总验证命令返回非零状态。

### 5.3 测试数据隔离

PostgreSQL 集成测试使用独立测试数据库或独立 schema，并满足：

- 测试名称或运行 ID 能定位其数据范围。
- 测试开始前创建或清理自己的范围。
- 测试结束后清理自己的范围。
- 不连接生产数据库。
- 不读取或修改真实账号、店铺、订单、商品、文件或任务。

### 5.4 生成产物策略

对以下路径分别验证来源和重建方式：

- Web 公共目录中的扩展解压副本
- 扩展 ZIP
- `desktop/dist`
- `desktop/dist-electron`

能够从已跟踪源代码稳定重建的产物不再作为手工源代码维护，并加入忽略规则。无法重建或缺少上游源代码的内容继续保留，标记为受控运行资产，并纳入完整性检查。

### 5.5 稳定基线验收

稳定基线必须同时满足：

- Git 工作区干净。
- 根验证命令全绿。
- 没有真实 Ozon 写操作。
- 没有生产数据迁移。
- 未验证范围有明确原因、风险和后续负责人。
- 每个分类提交能够独立回退。

## 6. 业务与数据安全边界

### 6.1 RequestContext

所有普通业务路由在进入 Service 前构造以下上下文：

```js
{
  actorId,
  accountId,
  storeId,
  dataCollectionStoreId,
  permissions,
  requestId
}
```

约束：

- `actorId` 和 `accountId` 来自服务端认证会话。
- `storeId` 必须通过当前账号的店铺归属校验。
- `dataCollectionStoreId` 必须通过当前账号的数据店铺归属校验。
- 普通业务操作必须具有 `tenant.operate`。
- 客户端提交的账号 ID、店铺 ID 只能作为选择请求，不能成为授权依据。
- Service 不得以 `state.currentAccountId`、`state.currentStoreId` 或 `state.currentDataCollectionStoreId` 作为默认租户范围。

旧的全局当前账号和店铺字段只允许存在于兼容适配层，不能成为新模块 contract 的一部分。

### 6.2 上架 payload 唯一来源

建立唯一上架 payload 构造模块，由 Web、扩展和服务端通过稳定 contract 调用或消费。以下字段不得由多个消费者分别计算：

- 售价和划线价
- VAT
- 币种
- 重量和尺寸
- 库存与仓库
- 类目、属性和字典值

真实提交路径禁止使用以下无依据兜底：

- 售价乘以 `1.25` 生成划线价
- VAT 默认为 `"0"`
- 币种缺失时猜测为 CNY 或 RUB
- 重量或尺寸缺失时填入 `100`

必要字段缺失时，预检返回稳定错误并拒绝创建任务。提交快照必须保存：

- 规则或配置版本
- 业务依据来源
- 币种
- 操作账号与店铺
- 确认时间
- 输入摘要
- 幂等键

### 6.3 稳定 API contract

关键接口采用独立的请求解析器和响应映射器，例如：

```js
parseCollectListingSubmitRequest(body, context)
toCollectListingJobResponse(job)
```

请求解析器负责字段类型、必填项、范围和枚举校验。响应映射器禁止直接暴露：

- 数据库表行
- 服务端全局状态
- 密钥和令牌
- Ozon 原始响应中的未审查字段

第一阶段使用纯 JavaScript contract 模块和自动测试，不为了统一格式引入大型框架。

### 6.4 审计、幂等与恢复

账号、店铺、权限、价格规则、采集、上架和外部同步操作记录：

- 操作人和租户范围
- 请求 ID 和幂等键
- 输入摘要与规则版本
- 原状态和目标状态
- 成功、失败或未知结果
- 错误码、重试和对账状态

外部写操作只允许进入幂等任务管线。路由不能直接调用 Ozon 写接口。超时但无法确定结果时进入对账状态，不能自动重复提交。

## 7. 渐进式模块拆分

拆分按以下顺序进行：

1. 上架 payload、预检和提交 contract
2. 租户权限与 RequestContext
3. 服务端账号、店铺、文件、模板、缓存、Browser Agent 和上架历史路由
4. Web 商品、采集箱、上架编辑、库存、订单、退货和模板页面
5. 扩展采集、上架桥接、同步、更新和 UI 模块
6. 桌面端源码来源确认及后续模块治理

每次迁出一个可独立验证的业务用例：

1. 先写当前行为 contract 测试。
2. 运行测试并确认测试锁定当前行为。
3. 移动最小范围代码，不改变可见行为。
4. 切换调用方到新模块。
5. 运行模块测试和根回归。
6. 下调对应巨型文件行数上限。
7. 单独提交。

`server/index.mjs` 最终只负责进程启动、依赖装配和路由注册。`app/src/App.jsx` 最终只负责应用壳和路由装配。

## 8. 错误处理

关键错误使用稳定错误码，至少区分：

- 未认证
- 权限不足
- 账号或店铺范围不匹配
- 请求 contract 不合法
- 业务规则未确认
- 状态迁移冲突
- 幂等键复用冲突
- 并发版本冲突
- 外部服务明确失败
- 外部结果未知、需要对账
- 持久化或迁移失败

前端根据错误码决定提示和恢复动作，不解析中文错误文本推断业务状态。

## 9. 测试与回归

### 9.1 每个改造包的测试

每个改造包至少覆盖：

- 正常输入
- 边界值和缺失字段
- 重复请求
- 权限不足和跨账号/跨店铺访问
- 合法与非法状态迁移
- 并发版本冲突
- 金额精度和币种不一致
- 未确认业务规则
- 外部超时、未知结果和恢复
- 数据库事务失败
- 消费者 contract

### 9.2 核心功能保护清单

根回归至少覆盖：

- 登录与多会话
- 账号和店铺隔离
- 商品、订单和库存同步
- 采集与采集箱
- 上架预检、任务队列和状态查询
- 算价配置与计算快照
- 文件存储和对象清理
- 扩展桥接
- 桌面采集任务

### 9.3 外部副作用隔离

自动测试只使用 mock、测试数据库和测试对象存储。真实 Ozon 写操作、真实店铺同步、生产迁移和密钥变更必须单独批准。

## 10. 交付、回滚与恢复

每个改造包完成时报告：

- 修改内容与文件
- Contract 变化
- 测试命令与结果
- 旧功能回归范围
- 未验证项及原因
- 数据和外部副作用
- 回滚或恢复步骤

应用代码优先通过回退该改造包的独立提交恢复。新增且向前兼容的数据库字段和表通常保留，通过关闭新路径或恢复旧消费者回滚应用，避免破坏已有数据。

外部任务发生未知结果时保留任务和审计记录，进入对账流程；不通过重复提交或删除记录伪造回滚。

## 11. 实施阶段划分

本设计拆成五个独立实施计划：

1. 保护性基线分类与提交
2. 根 workspace 与完整验证门禁
3. RequestContext、`tenant.operate` 与租户范围治理
4. 上架规则和 payload contract 收口
5. 巨型入口按业务用例渐进拆分

每个计划必须先达到独立可验收状态，再开始下一个。第三、第四项完成前，不把项目标记为适合任意功能扩展。
