# Ozon 完整商品采集补全设计

## 背景

当前扩展已经改为复用 Web 登录建立的账号级 Collector 会话，不再单独登录，也不再
绑定“数据店铺”。这一方向符合“账号级统一采集箱，上架时再选择目标经营店铺”的业务
规则，但旧扩展 `0.13.88.1` 使用的后端 Fleet 商品补全链路没有被 Collector 会话替代。

结果是：扩展仍能读取 Ozon 公共商品页的标题、图片、价格等字段，也可能通过当前
Seller 页面取得部分数据；但在 Seller 上下文不可用或平台接口返回不完整时，无法稳定
取得：

- `description_category_id`（产品类目）；
- 包装重量；
- 包装长、宽、高。

数据面板已经对这些字段执行完整性门禁，而商品详情页的“一键采集”仍可能在补全失败后
上传残缺数据，因此两个入口会产生不同结果。

## 目标

在不恢复扩展独立登录、不恢复数据店铺绑定、不让扩展负责店铺同步或发送同步指令的前提
下，实现与 `0.13.88.1` 相同或更严格的核心采集效果：类目、重量、长、宽、高全部补全
并持久化后，才显示“采集成功”。

## 非目标

- 不恢复扩展账号密码登录、Web Bearer token 或经营店铺选择。
- 不由扩展触发店铺商品、库存、订单等同步任务。
- 不在采集阶段确定上架目标店铺。
- 不重构与本次商品补全无关的 Ozon 同步、上架或订单模块。
- 不保证 Ozon 上游缺失的数据可以被猜测或生成；上游确实缺失时必须失败关闭。

## 验收标准

1. 打开支持的 Ozon 商品页面后，扩展在后台提前补全资料，但不自动写入采集箱。
2. 点击任一采集入口后，采集箱记录必须同时包含有效类目、重量、长、宽、高。
3. 缺少任一必填字段时，不显示“采集成功”，也不新增或覆盖为残缺记录。
4. 数据面板“采集”和商品详情页“一键采集”使用同一业务协调器，结果一致。
5. 相同账号、来源、SKU 和请求标识的重复点击或网络重试不会产生重复记录。
6. Web 未登录时提示先登录，并提供 Web 登录页跳转按钮。
7. 平台或网络暂时失败后可以安全重试；错误提示能区分登录、排队、未找到、字段缺失和
   网络故障。
8. 缓存、查询、保存和审计均按 Web 账号隔离，不允许跨账号复用数据或凭据。
9. 可追溯每次补全采用的数据来源、采集时间、缓存命中情况、上游响应摘要和失败原因。
10. 原有账号级采集箱、店铺同步、商品列表和上架时选择经营店铺的流程不变。

## 方案比较

### 方案 A：Collector 专用只读补全通道（采用）

为 Collector 会话增加范围狭窄的 `collector.ozon.read` 权限和只读商品补全接口。后端
从当前 Web 账号已有、有效的 Ozon 连接中选择可用连接，通过 Fleet 搜索和 bundle
接口取得完整字段；扩展不传店铺、公司编号或平台密钥。

配合页面展示时预取、账号级缓存和同 SKU 请求合并，缓存命中时点击采集只需校验并
保存。该方案保留当前账号模型，权限最小，速度和成功率最接近旧扩展。

### 方案 B：恢复扩展独立登录与店铺令牌（不采用）

实现最接近旧扩展，但会重新引入扩展账号密码、Web Bearer token、store ID 和数据店铺
状态，违反已经确认的产品方向，并扩大敏感信息暴露面。

### 方案 C：仅依赖当前浏览器 Seller 页面（不采用）

不需要后端新接口，但依赖 Seller 标签页、公司上下文和页面接口稳定性；页面未登录、
请求未发生或平台反爬时无法可靠补全，不能满足完整采集的验收标准。

## 总体架构

### 1. 后端只读补全服务

新增单一职责的 Ozon 商品补全服务。它只处理“给定当前账号与 SKU，返回可用于采集的
完整规范化商品资料”这一用例，不负责采集箱写入、店铺同步或上架。

服务依赖三个稳定接口：

1. `AccountOzonConnectionPort`：只返回当前账号有权使用的有效 Ozon 连接；连接选择与
   扩展输入无关。
2. `OzonProductEnrichmentPort`：执行 SKU 到内部 `variant_id` 的搜索，再调用 bundle
   取得类目、类型、重量、尺寸和变体数据。
3. `EnrichmentCacheRepository`：按账号和 SKU 读取、保存缓存及来源摘要，并提供带过期
   时间的原子查询租约，保证多进程不会重复调用同一上游商品查询。

连接选择规则固定为：只考虑当前账号拥有且状态有效的后端 Ozon 连接；优先最近一次
只读查询成功的连接，其余按稳定顺序尝试。连接 ID 只进入内部审计，不附着到采集商品，
因此不会形成“数据店铺绑定”。没有有效连接时返回明确错误，不借用其他账号连接。

### 2. 扩展补全客户端

新增 Collector 专用的只读补全客户端。它只持有现有 Collector session，并调用补全
接口；不得读取或保存 Web Bearer、Ozon API key、store ID 或 company ID。

本地 Seller 页面采集保留为辅助来源：后端暂时不可用时，可以尝试已有
`searchVariants` + bundle 路径。只有本地结果也通过同一完整性校验时才能保存；本地
结果不得携带经营店铺绑定信息。

### 3. 统一采集协调器

数据面板和商品详情页不再各自决定“补全失败后是否继续上传”，而是调用同一个采集
协调器。协调器负责：

- 预取和复用完整缓存；
- 统一字段和单位；
- 执行客户端完整性校验；
- 使用稳定请求标识调用现有账号级采集写入接口；
- 把稳定错误码转换为一致的中文提示。

这样可以修改某个数据来源的内部实现，而不改变两个页面入口的业务行为。

## 数据流

### 页面预取

1. 扩展从商品页面提取公共字段和 SKU。
2. 确认 Collector 会话有效且包含 `collector.ozon.read`。
3. 单商品页面调用 `POST /collector/ozon/enrich`；列表可调用
   `POST /collector/ozon/enrich/batch`，每批最多 20 个 SKU。
4. 后端先读取当前账号的完整缓存；未命中时取得同账号、同 SKU 的查询租约。租约持有者
   调用 Fleet 搜索和 bundle，其他请求等待同一缓存结果；租约超时可以被安全接管。
5. 后端统一为克和毫米，验证必填字段，记录来源摘要并返回结果。
6. 扩展把完整结果暂存在内存；预取阶段不调用采集写入接口。

### 点击采集

1. 协调器进入 `SAVING` 前必须拿到状态为 `COMPLETE` 的补全结果。
2. 若仍在预取，按钮显示“正在补全商品资料”并等待最多 20 秒；搜索、bundle、连接回退
   共用这一个截止时间。超时后允许重试，不上传残缺数据。
3. 客户端再次校验类目、重量、长、宽、高均为正数，再与公共页面字段合并。
4. 通过现有账号级采集接口保存；后端在持久化前再次执行相同的完整性门禁。
5. 只有持久化成功后进入 `SUCCESS` 并显示“采集成功”。

## API contract

### 单商品补全

`POST /collector/ozon/enrich`

请求体：

```json
{
  "requestId": "stable-client-request-id",
  "sku": "4862904234"
}
```

只接受 `requestId` 和 `sku`。请求中出现账号、store、company、经营店铺或数据店铺字段
时拒绝处理，而不是静默采信。

成功响应：

```json
{
  "ok": true,
  "data": {
    "status": "COMPLETE",
    "contractVersion": "collector.ozon.enrichment.v1",
    "sku": "4862904234",
    "descriptionCategoryId": 123,
    "typeId": 456,
    "logistics": {
      "weightG": 500,
      "lengthMm": 300,
      "widthMm": 200,
      "heightMm": 100
    },
    "variantData": {},
    "source": "BACKEND_FLEET",
    "capturedAt": "2026-07-31T00:00:00.000Z",
    "cache": {
      "hit": false,
      "expiresAt": "2026-07-31T06:00:00.000Z"
    }
  }
}
```

`descriptionCategoryId`、`weightG`、`lengthMm`、`widthMm`、`heightMm` 必须是有限正数；
`typeId` 可为空，不参与本次完整性门禁。上游单位先按接口 contract 解析，再显式换算；
单位不明时不猜测。

### 批量预取

`POST /collector/ozon/enrich/batch`

请求体包含一个批次请求标识和最多 20 个去重后的 SKU：

```json
{
  "requestId": "stable-batch-request-id",
  "skus": ["4862904234", "4862904235"]
}
```

响应使用 `{ok, data: [{sku, status, result?, error?}]}`，保持输入 SKU 顺序；每项只能为
`COMPLETE` 或 `ERROR`。`result` 使用单商品成功响应中的 `data` contract；`error` 固定为
`{code, message, missingFields, retryable}`。单个 SKU 失败不取消其他 SKU。后端对上游
访问采用受控并发，每账号固定最多 4 个，避免列表页造成请求风暴。批量请求同样拒绝
账号、store、company、经营店铺和数据店铺字段。

### 采集写入门禁

现有 `/sources/{source}/collect` 与批量接口仅在规范化来源为 Ozon 时，于写入之前增加
完整性校验；其他采集来源不应用这组 Ozon 字段规则。缺少必填字段时返回 HTTP 422、
错误码 `OZON_COLLECT_INCOMPLETE` 和 `missingFields`，不写采集箱、不写成功请求记录。

## 权限与数据边界

- Collector 默认权限新增 `collector.ozon.read`；补全路由必须在后端校验该权限。
- 旧 Collector session 不自动扩大权限。扩展发现缺少权限时，通过现有 Web 授权桥重新
  建立 Collector 会话；用户无需在扩展内输入账号密码。
- 补全服务从认证结果取得 `accountId`，忽略客户端可伪造的账号范围。
- 所有缓存键、并发合并键、查询、审计和连接选择都包含 `accountId`。
- 补全响应和日志不得包含 Ozon token、Cookie、Authorization、连接密钥或完整上游
  请求头。
- 采集记录继续保持 `storeId = null`；目标经营店铺只在上架阶段选择。

## 缓存、幂等与性能

- 完整结果缓存 6 小时，键为 `accountId + source + sku + contractVersion`。
- 未找到、字段缺失和上游临时失败最多负缓存 1 分钟；权限和登录错误不缓存。
- 点击采集发现缓存缺失或不完整时允许强制刷新一次，仍不完整则失败关闭。
- 同一进程内以缓存键合并正在执行的请求；持久缓存 repository 使用原子租约保证多实例
  对同一缓存键同时最多一个上游查询，失败或进程退出后可在租约过期时恢复。
- 预取不产生采集箱副作用。采集写入继续使用现有账号、来源、SKU 和 idempotency key
  contract；相同请求标识携带不同内容时返回冲突。
- 批量预取每批最多 20 个、每账号并发最多 4 个；这些上限由服务端固定并通过测试验证，
  不接受扩展覆盖。

## 状态与错误处理

统一协调器使用以下有限状态：

- `IDLE`：尚未预取；
- `PREFETCHING`：正在只读补全；
- `READY`：已有完整结果；
- `SAVING`：正在幂等写入采集箱；
- `SUCCESS`：后端已经持久化；
- `BLOCKED_AUTH`：Web/Collector 会话无效；
- `ERROR`：补全、网络或保存失败，携带稳定原因并允许安全重试。

不允许从 `PREFETCHING` 或不完整的 `ERROR` 直接跳到 `SUCCESS`。

稳定错误及用户提示：

| HTTP / 错误码 | 用户提示 | 是否可重试 |
| --- | --- | --- |
| 401 `COLLECTOR_AUTH_REQUIRED` | 请先登录 Web，并展示登录按钮 | 重新登录后 |
| 403 `COLLECTOR_PERMISSION_DENIED` | 请重新连接 Web 采集授权 | 重新授权后 |
| 404 `OZON_ENRICH_NOT_FOUND` | 未找到该商品的完整资料 | 可以 |
| 422 `OZON_ENRICH_INCOMPLETE` | 明确列出缺少的类目、重量、长、宽、高 | 可以 |
| 429 `OZON_ENRICH_BUSY` | 商品资料正在排队，请稍后重试 | 可以 |
| 502/504 `OZON_ENRICH_UPSTREAM_FAILED` | Ozon 商品资料暂时无法读取 | 可以 |
| 422 `OZON_COLLECT_INCOMPLETE` | 商品资料不完整，未写入采集箱 | 可以 |

重试复用同一业务请求标识；只有内容发生实质变化时生成新的内容哈希。任何失败都不能先
显示成功再异步修补。

## 可追溯与可观测性

每次后端补全记录脱敏的结构化事件，包括：账号、SKU、request ID、连接内部标识、缓存
命中、上游步骤、耗时、结果状态、缺失字段、响应摘要哈希和采集时间。成功写入的原始
采集 payload 继续进入现有原始响应留存流程。

不得记录令牌、Cookie 或完整授权头。日志使用 request ID 串联扩展补全、后端上游调用
和采集写入，便于定位“页面显示有数据但采集箱缺字段”等问题。

## 组件影响范围

预计修改范围：

- `server/collector-auth-service.mjs`：新增只读权限；
- 新的后端补全 Service、Fleet Port、缓存 Repository 和路由；
- 账号级采集写入的服务端完整性门禁；
- `extension/background/service-worker.js`：只读补全消息路由；
- 新的扩展补全客户端和统一采集协调器；
- `extension/content/ozon-data-panel.js` 与 `extension/content/ozon-product.js`：改为使用
  统一协调器；
- 对应后端 contract、权限、缓存、幂等、扩展状态和浏览器交互测试；
- 打包产物及源包一致性校验。

持久缓存采用独立 repository：JSON 模式写入新的账号级缓存集合；PostgreSQL 模式通过
向前兼容迁移新增独立补全缓存表，并以账号、来源、SKU、contract 版本建立唯一约束、
过期索引和短期查询租约字段。迁移不得修改或删除现有采集、店铺和上架数据。两种实现
必须遵循同一
repository contract；PostgreSQL 未启用时仍可运行和测试。账号删除流程必须同步清理
该账号的补全缓存和审计记录。

## 测试与验证

### 单元测试

- SKU、类目、重量和尺寸的解析、正数校验及单位换算；
- Fleet 搜索结果到 `variant_id` 的精确匹配和 bundle 合并；
- 缓存命中、6 小时过期、1 分钟负缓存、同 SKU 请求合并和过期租约接管；
- 协调器合法状态流转，禁止不完整结果进入保存或成功状态；
- 两个采集入口使用同一协调器 contract。

### 后端集成与 contract 测试

- 缺少 `collector.ozon.read` 被后端拒绝；新会话只得到声明的权限；
- 客户端伪造账号、store、company 字段被拒绝；
- 两个账号使用相同 SKU 时缓存、连接和审计完全隔离；
- 完整补全、未找到、字段缺失、上游超时、排队和重试错误响应稳定；
- 单进程和多实例重复补全都只执行一次上游查询，过期租约可恢复；重复采集不产生重复
  记录；
- 服务端门禁在五个字段任一缺失时不写任何残缺记录；
- JSON 状态和按配置启用的 PostgreSQL repository contract 一致。

### 扩展和端到端测试

- 页面打开触发预取但采集箱数量不变；
- 缓存命中时点击快速完成，冷缓存时显示“正在补全商品资料”；
- 数据面板和商品详情页对成功及每类错误显示一致；
- Web 未登录时显示登录入口，不调用受保护补全和写入接口；
- 网络中断后使用相同 request ID 重试，不产生重复商品；
- 实际 Ozon 测试商品在采集箱编辑页显示类目、重量、长、宽、高；
- 运行扩展完整测试、应用构建、Docker 配置检查、源目录/公开包/ZIP 一致性检查。

真实 Ozon Fleet 验证需要开发账号已有有效 Ozon 连接；自动化测试使用脱敏 fixture 和
可控 adapter，不调用生产平台。交付时必须单独说明真实平台验证是否执行及结果。

## 回归范围

- Web 登录到 Collector session 的签发、交换、续期和注销；
- 账号级统一采集箱及去重；
- 商品详情页和数据面板公共字段采集；
- 店铺商品同步仍只由 Web 后端负责；
- 商品列表、采集箱编辑和上架时选择经营店铺；
- 未启用 PostgreSQL 与启用 PostgreSQL 两种配置路径。

## 回滚与恢复

后端补全接口和扩展预取可作为一个功能单元回滚；回滚后恢复为当前 Seller 本地补全
路径，不影响既有采集箱和店铺数据。新增缓存数据没有业务所有权，可安全过期或在确认
精确范围后清理；兼容数据库迁移不回删旧字段或旧表。

如果新接口短时异常，扩展只允许使用通过完整性校验的本地 Seller 结果；否则明确失败，
绝不降级为保存残缺商品。重新部署修复版本或恢复接口后，用户使用原请求重试即可恢复，
不会产生重复记录。
