# 自动上架 AI 运行与进度可视化设计

## 目标

修复自动上架任务长期停留在“正在规划图片内容”且最终只显示笼统失败的问题，并让用户能看到任务到底是在排队、执行还是等待重试。

## 已确认根因

1. 本地开发入口只启动 API、上架 worker、前端代理和页面，没有启动专用 `auto-listing-ai-worker`。规划消息因此长期留在待领取状态。
2. AI 图片规划使用的严格 JSON Schema 中，`language` 等常量或枚举节点缺少显式 `type`。当前 Sub2API/OpenAI 兼容入口拒绝该 schema，三次规划均以 `RETRYABLE_GATEWAY` 失败。
3. 任务列表只公开商品状态，不公开安全的队列阶段、执行状态、尝试次数和最后更新时间；“排队”和“正在调用 AI”都被合并成同一句话。

## 业务规则

- 本地统一开发入口必须同时启动专用 AI worker；生产 Docker composition 保持现有独立 worker 部署。
- 规划和富文本的严格 JSON Schema 中，每个常量或枚举叶子都必须携带明确类型，避免网关逐项拒绝。
- 页面进度只来自当前租户、当前商品的持久化 outbox 与状态记录，不从内存猜测，也不显示原始 prompt、模型响应、凭据或供应商错误。
- 用户可见阶段闭合为：等待后台领取、AI 正在执行、等待重试、已完成、执行失败。显示尝试次数、最后更新时间和下一次重试时间（若存在）。
- 当前失败任务只在代码和回归验证通过后执行一次显式重试；不批量重试历史任务，也不删除审计记录。
- 重试继续使用现有账号、任务、商品、状态版本和幂等边界，不新增旁路数据库写入。

## 数据与接口

- 仓储读取任务时，对每个可见 item 额外读取其最新一条新合同 AI outbox，按 `created_at/id` 确定当前阶段。
- 服务公开一个闭合 `workflowProgress` DTO：
  - `phase`: 当前持久化阶段或 `null`；
  - `state`: `QUEUED | RUNNING | RETRY_WAIT | COMPLETED | FAILED | IDLE`；
  - `attemptCount`: 非负整数；
  - `updatedAt`: 规范 UTC 时间或 `null`；
  - `nextRetryAt`: 规范 UTC 时间或 `null`。
- 前端只接受该精确 DTO；字段缺失、额外字段、代理、访问器、非法时间或非法组合均失败关闭。
- 页面状态列在主状态下展示安全的进度说明，例如“等待后台领取 · 已尝试 0 次”或“AI 正在执行 · 第 1 次”。

## 验收标准

- Schema 单测先复现缺少显式类型，再确认所有常量/枚举叶子闭合。
- 开发入口合同测试先复现缺少 AI worker，再确认统一入口包含且只包含一个专用 worker。
- 仓储、服务和前端测试覆盖六种进度状态、多租户隔离、最新 outbox 选择及 hostile DTO 拒绝。
- 相关 AI planner/worker/retry、自动上架服务、仓储和页面回归通过。
- 使用本地 Sub2API 对当前任务执行一次显式重试；记录任务状态、尝试数和外部调用结果，不重试其他历史任务。

## 风险与回滚

- AI 重试可能产生一次付费文本规划调用；用户已明确授权本次当前任务重试。
- 若网关仍拒绝 schema，停止继续重试并保留稳定错误证据，不循环付费调用。
- 应用改动按独立提交回滚；进度为只读派生，无数据库迁移。
- 已有失败尝试是审计记录，不删除、不改写。
