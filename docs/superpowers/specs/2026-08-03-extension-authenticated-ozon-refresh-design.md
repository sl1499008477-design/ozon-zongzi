# 扩展认证成功后刷新 Ozon 页面设计

## 背景与根因

Web 页面已经登录，扩展后台也已经成功取得账号级 Collector 会话，但已打开的 Ozon 页面仍可能显示“请登录 Web”。原因是页面在登录前缓存了未登录结果，Collector 会话建立后没有触发页面重新读取扩展后台状态。实际验证中，刷新 Ozon 页面后登录提示立即消失，数据面板恢复加载。

## 业务目标与验收标准

- Collector 票据交换成功后，自动刷新已经打开的 Ozon 买家页面一次。
- 刷新后数据面板重新读取 Collector 会话，不再保留旧的“未登录”界面。
- Seller 页面不得刷新，避免影响登录、店铺切换和未保存操作。
- 票据交换失败、尚未登录或普通状态检查不得刷新页面。
- 同一轮认证产生的连续触发由现有防抖合并，不能形成循环刷新。

## 方案

在扩展后台 `collector.auth.exchange` 成功分支中，完成会话保存后调用现有 `reloadOzonTabs()`。

该函数已有明确边界：

- 只查询 `ozon.ru`、`www.ozon.ru`、`ozon.kz`、`www.ozon.kz` 的买家页面；
- 不匹配 `seller.ozon.ru`；
- 使用 300 毫秒防抖，把同一时间窗口内的重复触发合并为一次刷新；
- 不修改 Web 登录状态、Collector 会话、店铺配置或数据库数据。

不采用页面轮询，也不为三个不同数据面板分别增加认证事件协议。这能复用现有稳定边界，并减少跨模块状态同步和回归范围。

## 数据流

1. Web 页面确认用户已登录并申请一次性 Collector 票据。
2. 扩展后台使用票据建立 Collector 会话。
3. 只有交换成功后，扩展后台安排一次 Ozon 买家页面刷新。
4. 页面重新加载后调用 `getAuth`，读取到已认证状态并加载数据面板。

## 失败与边界处理

- 票据过期、无效、网络失败或父 Web 会话失效：保持现状并返回稳定错误，不刷新页面。
- 没有打开 Ozon 页面：查询结果为空，不产生副作用。
- 多个 Ozon 页面：每个已打开的买家页面刷新一次。
- Seller 页面：始终排除。
- 刷新 API 单个页面失败：不影响已建立的 Collector 会话；沿用现有后台行为。

## 测试与回归

- 先增加失败测试，证明当前成功交换后没有刷新 Ozon 页面。
- 验证成功交换会触发现有防抖刷新逻辑。
- 验证交换失败不会刷新。
- 验证刷新查询范围不包含 Seller 页面。
- 运行 Collector 认证、扩展后台运行时和扩展完整相关回归。
- 在真实 Chrome 中保持 Web 已登录，确认 Ozon 页面自动恢复为已认证数据面板。

## 影响、回滚与未涉及范围

- 代码影响仅限扩展后台认证成功分支及对应测试。
- 不修改 API contract、数据库表、生产数据库数据或权限模型。
- 如出现问题，撤销该提交即可恢复为“用户手工刷新 Ozon 页面”的旧行为。
