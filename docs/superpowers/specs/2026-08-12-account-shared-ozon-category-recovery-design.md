# 账号内共享 Ozon 类目与自动失效恢复设计

日期：2026-08-12

状态：业务设计已确认，实施计划已完成

实施计划：`docs/superpowers/plans/2026-08-12-account-shared-ozon-category-recovery.md`

## 目标

1. 采集商品时保存可靠的 Ozon 源类目，上架时直接复用，不再按目标店铺重复匹配。
2. 同一系统账号内的所有 Ozon 店铺共享类目结果；不同系统账号之间严格隔离。
3. 只有 Ozon 明确判定类目不存在、失效或调整，并且确认商品没有创建成功时，系统才自动刷新类目、重建类目相关属性并续跑一次。
4. 没有可靠源类目时先通过 Ozon 商品 ID 或 SKU 补查；仍然无法取得时只提供候选并要求人工确认，不允许无依据自动上架。
5. 发布新版本时删除旧的按店铺类目解析数据，不把旧店铺级结果迁入新表。
6. 采集箱和自动上架共用同一套类目证据、共享结果、恢复状态与审计合同。

## 被取代的旧决策

本文档取代 `2026-08-12-auto-listing-category-handoff-latest-task-design.md` 中“按当前店铺精确交接类目”的设计，以及对应实施计划中的店铺级类目交接部分。

原设计中以下两个独立需求不受影响：

- 同一“采集商品 + 上架店铺”在普通列表中只展示最新任务，数据库仍保留任务历史；
- 任务表格显示真实创建时间。

已经开始但尚未合并的店铺级类目交接实现不得继续推进。后续实施计划必须以本文档为类目业务依据。

## 已确认业务规则

### 类目共享范围

- 类目属于 Ozon 平台体系，不以目标店铺作为匹配维度。
- 同一系统账号下的多个 Ozon 店铺共用类目结果。
- 不同系统账号之间不能查询、复用、更新或失效对方的类目数据。
- 店铺凭据仍用于 Ozon API 权限、商品导入、品牌资质、价格、仓库和库存等店铺级操作；取消店铺级类目匹配不等于取消其他店铺边界。

### 首次使用顺序

1. 采集入口保存源商品的类目证据。
2. 如果该源类目已有账号内共享的有效修复结果，使用修复后的当前类目。
3. 否则直接使用采集到的源类目，不为每个店铺重新匹配。
4. 在生成或提交前仍执行本地结构校验：类目 ID、类型 ID 和必填类目属性必须完整，不能把不完整数据发送给 Ozon。

“直接使用源类目”只表示不做店铺级匹配，不允许跳过输入完整性、金额币种、权限、资质、仓库或库存校验。

### 没有源类目

1. 优先使用采集时保存的 Ozon 商品 ID、SKU 或其他稳定来源标识，通过只读 Ozon 接口补查原商品类目。
2. 补查成功后保存为新的源类目证据并继续。
3. 补查仍失败时，可根据标题、属性和图片生成类目候选，但候选只能供管理员选择。
4. 管理员未确认前不得进入付费 AI 生成或 Ozon 商品写入阶段。
5. 人工确认结果成为账号内共享结果，并记录确认人、时间和依据。

## 数据合同

### 源类目证据

每个采集商品保留闭合、可追溯的源类目证据，至少包括：

- 系统账号 ID；
- 采集商品 ID 和源版本；
- Ozon 商品 ID、SKU 或能够补查源商品的稳定标识；
- 源 `description_category_id`；
- 源 `type_id`；
- 规范化类目路径和安全属性摘要；
- 来源类型、采集时间和证据版本；
- 原始响应的后台受限引用或哈希，不向普通页面返回任意原文。

源证据属于采集事实，不能因一次上架失败而被覆盖。新的采集版本产生新的证据版本。

### 账号内共享类目结果

新增独立的账号级共享类目合同。记录按以下稳定来源签名区分：

```text
accountId
+ sourceDescriptionCategoryId
+ sourceTypeId
+ taxonomyScope
```

规范化类目路径及其哈希只作为来源证据和冲突排查信息，不进入共享结果唯一键，避免语言或展示路径变化把同一 Ozon 类目拆成多份。`description_category_id` 和 `type_id` 缺任一项时不得创建共享签名，必须先进入补查或人工确认流程。

共享结果至少包括：

- 当前 `description_category_id` 与 `type_id`；
- 状态：`ACTIVE | INVALIDATED | NEEDS_REVIEW`；
- 来源：`SOURCE_DIRECT | OZON_REFRESH | MANUAL`；
- 类目体系版本或指纹；
- 匹配或确认依据摘要；
- 创建、验证、失效和更新时间；
- 最近一次明确类目错误的安全码引用；
- 乐观版本号，防止并发刷新覆盖更新结果。

任何读取和更新都必须带 `accountId`。共享结果不得含目标店铺 ID，也不得把某个店铺的权限或资质误写成类目事实。

### 旧店铺级记录的删除

发布升级采用维护窗口，流程为：

1. 停止采集类目任务、自动上架创建和相关 worker，禁止旧程序继续写入；
2. 创建并验证可恢复的数据库备份；
3. 从采集源证据构建账号级共享类目数据，不采用旧店铺级匹配结果作为新数据来源；
4. 执行完整性、账号隔离和重复签名检查；
5. 在同一次 forward-only 数据库升级中启用新表，并删除旧店铺级解析表、记录、旧类目解析任务和仅服务旧解析逻辑的缓存数据；自动上架任务历史与审计不删除；
6. 部署只读写新合同的程序；
7. 完成数据库、HTTP 和页面冒烟检查后恢复 worker。

旧店铺级类目值不得复制到新共享表。已有不可变审计事件只作为历史操作证据，不得再参与类目决策；不对已有审计记录做破坏性改写。

由于旧表会被删除，这次升级不能只靠代码回退。失败恢复方式是停止服务、恢复升级前数据库备份并恢复旧程序。迁移一旦在生产完成并验收，后续数据库调整必须继续使用 forward-only 迁移。

## 自动失效恢复状态流

### 正常提交

1. 冻结本次商品使用的源证据、共享类目版本、属性版本、商品 `offer_id` 和业务幂等键。
2. 向 Ozon 提交一次商品导入。
3. 保存 Ozon `task_id`，通过 `/v1/product/import/info` 查询异步终态。
4. 成功则继续现有库存和后续流程，不触发类目匹配。

### 可自动修复的明确类目失败

只有同时满足以下条件才进入自动修复：

- 导入状态已经终结为失败；
- Ozon 结构化错误明确指向 `description_category_id`、`type_id`、新类目字段，或维护的确定性类目失效安全码；
- 商品没有返回有效 `product_id`；
- 通过 `offer_id` 的只读协调确认商品没有被创建；
- 该商品在本次业务操作中尚未执行过自动类目修复。

错误分类必须以 Ozon 的结构化 `code`、`field`、`attribute_id`、`state` 和终态为依据，不允许仅匹配自然语言错误文本。允许自动修复的错误码和字段组合使用版本化闭集；未知组合一律停止自动修复并进入人工排查。

满足条件后：

1. 原子地把当前共享类目版本标记为 `INVALIDATED`，保存安全错误证据；
2. 使用源证据读取最新 Ozon 类目体系并执行一次唯一匹配；
3. 读取新类目的必填属性和字典值；
4. 重新映射能够被可靠复用的源属性；
5. 只有“类目唯一匹配 + 所有必填属性完整 + 本地合同校验通过”才算修复成功；
6. 保存新的账号级共享结果和版本；
7. 复用已冻结的商品内容和图片，重建类目相关商品底稿；
8. 以新的子尝试 ID、相同业务幂等身份自动重新提交一次；
9. 成功后继续上架，不要求用户重新操作。

### 禁止自动类目重试的情况

以下情况不能触发类目刷新或直接再次导入：

- 网络超时、连接中断或响应丢失；
- Ozon 任务仍在处理中；
- 无法确认商品是否已经创建；
- 认证、权限、限流、服务端临时错误；
- 品牌、证书、销售权限、价格、币种、仓库或库存错误；
- 普通属性错误，但没有证据证明类目失效；
- 本次业务操作已经自动修复过一次。

结果不确定时先协调原 `task_id` 和 `offer_id`。在确认原写入结果前，不得创建新的商品导入副作用。

### 自动修复失败

出现以下任一情况时转为 `NEEDS_REVIEW` 并停止：

- 找不到唯一新类目；
- 新类目必填属性无法从源数据可靠补齐；
- 最新类目接口返回确定性无效数据；
- 第二次导入仍然失败；
- 发现商品可能已经创建或状态冲突。

普通用户页面只显示安全中文原因和建议动作；后台审计保留原 Ozon 任务、结构化错误、类目变更前后值、匹配依据、操作者和时间。

## 采集箱行为

- 采集箱保存源类目证据，不再为每个店铺生成独立解析结果。
- 已有有效账号级共享结果时，采集商品可直接展示当前共享类目。
- 没有共享结果时仍展示源类目，不因为尚未选择上架店铺而阻断采集。
- 没有源类目时执行一次只读补查；补查失败则显示“需要确认类目”，不自动猜测写入。
- 人工确认和 Ozon 失败后的自动修复都更新同一账号级共享合同，之后该账号内其他店铺可复用。

## 页面与安全错误

任务页面使用固定状态和安全文案：

- `使用采集类目准备上架`；
- `Ozon 类目已失效，正在自动修复`；
- `类目已重新匹配，正在继续上架`；
- `无法确认商品类目，请人工选择`；
- `Ozon 返回结果不明确，正在核对原任务`。

页面不得显示任意后端异常文本、凭据、完整 Ozon 响应或数据库结构。管理员排查视图可以读取闭合的结构化错误摘要和 correlation ID，但不能返回密钥、Authorization 头、完整商品内容或任意第三方文本。

列表“同一商品 + 上架店铺只显示最新任务”和“显示真实创建时间”的已确认行为继续保留，不受账号级类目共享调整影响。

## 模块边界

实现保持以下职责分离：

1. **源类目证据端口**：只负责保存和读取采集事实。
2. **账号共享类目仓储**：只负责账号隔离、版本、状态和原子更新。
3. **类目匹配服务**：输入源证据与当前 Ozon taxonomy，输出唯一匹配或结构化失败，不执行商品写入。
4. **导入结果分类器**：把 Ozon 异步终态归一为成功、明确类目失败、其他确定失败或未知，不访问数据库。
5. **类目恢复编排器**：执行一次失效、刷新、属性重建和安全重试状态流。
6. **Ozon 导入协调器**：维护 `task_id`、`offer_id`、写入尝试和不确定结果协调，防止重复商品。
7. **页面投影**：只消费安全状态和动作，不自行判断错误文本或类目有效性。

## 测试与验收

### 数据迁移

- 使用升级前真实结构的临时 PostgreSQL 验证新表生成、账号隔离和 forward-only 迁移。
- 新共享数据只来自源证据或新人工确认，不来自旧店铺级匹配行。
- 旧店铺级解析表和旧任务、缓存数据在成功升级后不存在。
- 任一预检失败时迁移整体失败，旧数据保持不变。
- 备份恢复演练能够恢复旧数据库与旧程序合同。

### 正常类目复用

- 当前商品 `collect_ccab18d873aa2c8074555143` 使用已采集源类目创建非阻断任务。
- 同一账号的两个店铺复用同一共享类目，不产生两份店铺级解析。
- 第二账号不能读取或更新第一账号的共享结果。
- 源类目完整时，创建任务阶段不调用店铺专属类目匹配。

### 无源类目

- 使用 Ozon 商品 ID 或 SKU 的只读补查成功后继续。
- 补查失败时只生成候选并阻断写入。
- 未经管理员确认的候选不能进入付费 AI 或 Ozon 导入。

### 明确类目失效

- fake Ozon 首次返回结构化类目失效终态且确认未创建商品；系统失效旧版本、匹配新类目、补齐必填属性并自动续跑一次。
- 第二次成功后继续库存流程，用户无需重新提交。
- 类目匹配不唯一或必填属性缺失时零第二次 Ozon 商品写入，并显示安全错误。
- 第二次仍失败时停止，不进行第三次导入。

### 不确定结果与幂等

- 首次提交响应丢失时先协调原任务，零重复商品导入。
- 已返回 `product_id`、按 `offer_id` 能查到商品或状态仍处理中时，零类目重试。
- 认证、限流、品牌、证书、币种、仓库和库存错误不会误触发类目刷新。
- 重复页面点击、worker 重启和响应重放不会增加 Ozon 商品写入次数。

### 回归

- 采集箱新增、编辑、补查和人工确认；
- 自动上架创建、付费 AI 边界、上传、异步导入协调和库存恢复；
- FBS、RFBS、账号、店铺、币种、仓库和凭据隔离；
- 最新任务列表、真实创建时间和历史审计读取；
- 应用生产构建、迁移静态检查和 disposable PostgreSQL 集成测试。

真实 Ozon 商品写入、真实付费 AI 和生产数据库不得用于自动测试；使用 loopback fake Ozon、受控 AI fixture 和一次性 PostgreSQL。生产发布必须单独经过备份、维护窗口和人工验收授权。

## 回滚与恢复

### 发布前或迁移失败

数据库事务回滚，继续使用旧程序；不得删除备份。

### 旧表删除后发现问题

1. 停止全部相关 worker 和写入入口；
2. 恢复升级前数据库备份；
3. 恢复旧程序版本；
4. 核对 Ozon 中已经发生的商品写入，再决定是否重放本地任务；
5. 不通过反向迁移猜测重建已删除的店铺级数据。

### 新版本验收后

后续修复使用新的 forward-only 迁移。账号级共享类目、源证据、恢复尝试和审计记录不得通过手工 SQL 任意改写。
