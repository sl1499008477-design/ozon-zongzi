# 本地 sub2API 与 AI 模型配置设计

日期：2026-08-08

状态：已确认，待实施计划

适用范围：`ozon 粽子` 自动上架功能的本地 AI 网关部署、模型发现、配置、测试与发布

## 1. 背景

自动上架后端已经具备 sub2API 网关适配、AI 配置版本、能力测试和任务配置锁定等基础能力，但当前仍存在两个使用闭环缺口：

1. 本机没有运行可访问的 sub2API，因此没有可打开的 sub2API 管理后台。
2. `ozon 粽子` 只有 AI 配置管理接口，没有管理员可直接使用的 Web 配置页面；模型名称仍需通过后台接口写入。

本设计补齐上述闭环，同时保持 sub2API 与现有业务系统低耦合。sub2API 负责上游 AI 账号、配额和网关 Key；`ozon 粽子` 负责自动同步可用模型、推荐候选模型，并由管理员确认文字模型和图片模型。

## 2. 业务目标

管理员能够在当前电脑上完成以下流程，无需手工调用后台接口：

1. 一键启动独立的本地 sub2API 环境。
2. 打开 sub2API 管理后台，配置上游 AI 账号或供应商 API Key。
3. 在 sub2API 中创建专用于 `ozon 粽子` 的网关 Key。
4. 在 `自动上架` 页面进入独立的 `AI 模型配置` 页面。
5. 输入 sub2API 网关地址和网关 Key。
6. 自动同步 sub2API 可用模型列表。
7. 由系统推荐文字模型与图片模型，管理员确认选择。
8. 管理员明确触发一次真实能力测试。
9. 测试通过后发布配置，供新建自动上架任务使用。

同一配置页面未来直接用于生产环境；生产环境仅替换 sub2API 地址、网关 Key和部署密钥，不另行开发第二套配置系统。

## 3. 非目标

本次不做以下事项：

- 不重写 sub2API 自带的上游账号、额度、计费和网关 Key 管理后台。
- 不让 `ozon 粽子` 直接读取或操作 sub2API 数据库。
- 不让浏览器直接携带网关 Key 调用 sub2API。
- 不根据模型名称直接认定模型一定具备文字或生图能力。
- 不在每日模型同步时逐个调用付费模型。
- 不允许 Web 服务直接操作 Docker 守护进程。
- 不改变采集箱、店铺、商品、订单或浏览器扩展的运行方式。

## 4. 系统边界与职责

### 4.1 sub2API

sub2API 独立负责：

- 上游 AI 服务商账号、OAuth 或 API Key。
- 上游账号池、额度、计费和转发。
- 向 `ozon 粽子` 发放下游网关 Key。
- 提供兼容接口，包括模型列表、文字生成和图片生成接口。

### 4.2 ozon 粽子

`ozon 粽子` 独立负责：

- 加密保存专用 sub2API 网关凭据。
- 通过自身后端访问 sub2API。
- 同步和缓存可用模型清单。
- 推荐文字模型和图片模型候选。
- 执行管理员明确触发的真实能力测试。
- 发布不可变配置版本。
- 创建自动上架任务时锁定配置版本。

### 4.3 调用路径

正式调用路径固定为：

`浏览器配置页面 → ozon 粽子后端 → sub2API → 上游 AI 服务商`

浏览器不得直接获得 sub2API 网关 Key；所有权限、账号边界、凭据解密、同步、测试和发布均在后端执行。

## 5. 本地部署设计

### 5.1 部署方式

项目提供一套明确、可重复的一键本地启动配置，但 sub2API 仍作为独立服务运行：

- 使用经过验证并固定版本的官方 sub2API 镜像，不使用不固定的 `latest`。
- sub2API、PostgreSQL 和 Redis 使用独立容器。
- 使用独立网络、独立数据卷和独立数据库账号。
- 所有端口默认只绑定 `127.0.0.1`。
- sub2API 管理后台默认地址为 `http://127.0.0.1:8080/`。
- 启动前检查 Docker 可用性和端口占用。
- 重启容器或电脑后保留数据。
- 升级必须显式执行，普通启动不得隐式升级镜像或数据库。

### 5.2 运维入口

提供稳定的本地操作入口：

- 启动 sub2API 本地环境。
- 停止 sub2API 本地环境。
- 查看健康状态。
- 查看经过脱敏的运行日志。
- 显式升级。
- 说明如何备份和恢复独立数据卷。

Web 页面只检测 sub2API 是否健康并提供管理后台链接，不挂载 Docker socket，也不从浏览器启动或停止容器。

### 5.3 隔离要求

- sub2API 不复用 `ozon 粽子` 的 PostgreSQL 或 Redis。
- sub2API 故障不得影响现有 Web 登录、采集、店铺同步、商品、订单或扩展端。
- 关闭自动上架和 AI 配置功能开关后，不初始化相关运行时任务和外部连接。

## 6. Web 页面设计

### 6.1 入口与权限

- 左侧导航仍保留 `AI 工具 → 自动上架`，不新增常驻左侧菜单项。
- `自动上架` 页面右上角增加 `AI 模型配置` 按钮。
- 按钮仅对拥有 `AI_CONTENT_MANAGE` 权限的管理员显示。
- 点击按钮进入独立配置路由。
- 后端必须再次校验权限，不能依赖前端隐藏按钮。

### 6.2 页面区域

页面包含四个区域。

#### sub2API 连接

显示：

- 运行状态：未启动、连接正常、连接异常。
- 网关地址。
- 网关 Key 状态；完整 Key 不可回显。
- sub2API 版本（网关可提供时显示）。
- 最近连接检查时间。
- `打开 sub2API 后台` 按钮。
- `测试连接` 按钮。

#### 模型同步与选择

显示：

- 最近一次成功同步时间。
- 同步结果和安全化错误信息。
- `立即同步` 按钮。
- 文字模型候选列表。
- 图片模型候选列表。
- `系统推荐` 标记及可解释的推荐依据。
- 管理员最终选择控件。

#### 能力测试与发布

操作顺序固定为：

`保存草稿 → 同步模型 → 选择模型 → 能力测试 → 发布启用`

能力测试前明确提示可能产生少量模型费用。测试结果分别显示：

- 文字结构化输出是否通过。
- 图片生成是否通过。
- 图片是否可正常解码。
- 响应耗时。
- 安全化错误原因。
- 测试时间和对应配置版本。

未通过测试或测试证据已过期的配置不能发布。

#### 当前配置与历史版本

显示：

- 当前正式版本。
- 网关地址。
- 文字模型和图片模型。
- 启用时间和操作管理员。
- 历史版本及其状态。
- 安全回退入口。

历史版本回退前必须重新验证凭据和模型能力。不能因为历史上测试通过就盲目恢复。

## 7. 网关凭据设计

### 7.1 输入与展示

- 管理员可在 Web 页面输入新的 sub2API 网关 Key。
- 保存后只显示 `已配置` 和必要的非敏感识别信息。
- 任何读取接口均不得返回完整 Key、密文、随机数或加密标签。
- 管理员只能创建新版本或覆盖更换，不能重新查看或复制旧 Key。

### 7.2 加密保存

- 使用带认证的加密方式保存网关 Key，防止密文被静默篡改。
- 数据库只保存密文、密钥版本、必要加密元数据和不可逆识别摘要。
- 加密主密钥不得进入业务数据库、日志、Git 或前端响应。
- 本地部署生成独立、仅当前操作系统用户可读的密钥文件，并加入忽略规则。
- 生产环境从服务器环境变量或外部密钥管理服务加载主密钥。
- 主密钥缺失、格式错误或解密失败时必须失败闭合，不允许降级为明文保存。

### 7.3 Key 更换

- 新 Key 先创建为待验证凭据版本。
- 使用新 Key 完成连接检查、模型同步和能力测试。
- 全部通过后才允许切换为正式配置。
- 测试失败时保留原正式配置。
- 正在执行的任务继续使用创建时锁定的配置证据。
- 新建、测试、启用、停用和失败均写入审计。

`ozon 粽子` 不负责在 sub2API 中撤销旧网关 Key；管理员确认无任务依赖后，在 sub2API 后台完成撤销。

## 8. 模型同步与推荐

### 8.1 同步规则

- 首次保存并验证连接后立即同步。
- 此后每 24 小时安排一次后台同步。
- 管理员可点击 `立即同步`。
- 同一账号同一网关只允许一个有效同步任务，重复请求复用原结果。
- 模型清单必须带账号、网关配置版本、同步批次和时间边界。
- 同步只读取模型清单，不逐模型执行真实生图。

### 8.2 推荐规则

同步结果先形成待验证候选：

- 文字模型优先考虑结构化输出、目标协议和可用状态。
- 图片模型优先考虑图片生成、参考图输入、目标尺寸和质量参数。
- 模型名称、供应商标识和网关元数据只能作为辅助评分证据。
- 推荐结果必须展示依据，不得假装已经完成真实能力验证。
- 管理员必须确认文字模型和图片模型。

### 8.3 已发布模型变化

- 新发现的模型只加入候选列表，不自动替换正式配置。
- 一次同步失败只记录异常，不判定正式模型失效。
- 成功同步后确认正式模型不存在或不可用时，将配置标为降级状态并阻止创建新的自动上架任务。
- 管理员重新选择、测试并发布后恢复。
- 已启动任务继续使用其锁定版本，不被同步结果中途改写。

## 9. 真实能力测试

管理员确认候选模型后，系统执行一次最小但真实的测试：

1. 调用文字模型生成固定的小型结构化结果，并严格校验结构。
2. 调用图片模型生成一张最低成本的测试图。
3. 验证返回图片的真实格式、尺寸和可解码性。
4. 核对请求模型与网关返回的模型证据。
5. 记录耗时、测试时间、配置版本和安全错误码。

测试具有幂等边界：相同配置、相同测试意图和仍有效的完成证据应返回原结果；响应超时或结果不确定时不得重复产生不可控的付费副作用。需要重试时创建有明确依据的新测试尝试。

自动化测试使用本地假网关或受控夹具，不调用真实付费模型。只有管理员在页面明确点击后才允许真实能力测试。

## 10. 配置发布与任务锁定

- 草稿、测试通过和正式发布为不同状态，禁止任意跳转。
- 发布必须校验：权限、账号边界、凭据版本、网关地址、模型清单、能力测试证据和预期配置版本。
- 发布请求必须幂等。
- 同一账号同一时刻只能有一个正式 AI 网关配置版本。
- 自动上架任务创建时冻结配置版本、文字模型、图片模型、协议和必要测试证据。
- 后续修改正式配置只影响新任务。
- 历史任务不得在执行中静默换模型。

## 11. 数据与接口边界

### 11.1 数据

复用现有 AI 网关配置、版本、能力测试和审计结构；仅在确有必要时新增兼容迁移，用于：

- 加密网关凭据及其版本。
- 模型清单快照和同步运行记录。
- 推荐结果和推荐依据。
- 配置与凭据版本的稳定关联。

数据库变更采用追加式迁移，兼容现有数据，不覆盖或删除历史审计。

### 11.2 稳定接口

后端提供按用例划分的稳定接口：

- 读取配置页面概览。
- 创建待验证网关凭据。
- 测试网关连接。
- 触发或查询模型同步。
- 保存候选模型选择。
- 触发或查询能力测试。
- 发布配置版本。
- 查询历史版本。
- 请求安全回退。

接口不得把数据库行直接暴露给前端。账号 ID 从认证上下文获得，不接受前端指定其他账号范围。

## 12. 安全、幂等与审计

- 所有管理操作在后端校验 `AI_CONTENT_MANAGE` 权限。
- 查询、更新、任务、缓存和审计均带明确账号边界。
- 保存、同步、测试、发布、更换 Key 和回退均要求幂等键与预期版本。
- 网络超时、重复点击和响应丢失不能创建重复配置或重复付费测试。
- 日志不得记录网关 Key、密文、授权头、原始上游错误体或敏感请求内容。
- 审计记录操作类型、操作者、账号、时间、配置版本、结果和安全错误码。
- 管理接口仅返回明确允许的稳定错误码，未知内部错误统一安全映射。

## 13. 失败与恢复

- sub2API 未启动：页面显示明确状态和本地启动指引；其他业务正常运行。
- sub2API 暂时不可达：保留上一正式配置和模型缓存，不删除数据。
- 新 Key 无效：待验证版本失败，原正式配置不变。
- 模型同步失败：允许安全重试，不立即停用现有配置。
- 能力测试失败：禁止发布，保留测试证据和安全错误原因。
- 能力测试结果不确定：不得当作成功，进入可恢复状态。
- 发布并发冲突：返回版本冲突并重新加载当前状态。
- 服务或数据库重启：持久化同步和测试任务可以继续处理，不重复执行已确认副作用。

## 14. 验收标准

### 14.1 本地部署

- 本机可以一键启动、停止和检查 sub2API。
- 管理后台只通过本机地址访问。
- 重启容器后上游账号和网关配置仍存在。
- sub2API 数据库和 Redis 与业务系统完全隔离。

### 14.2 配置页面

- 管理员可从自动上架页进入独立配置页。
- 普通用户看不到入口且直接调用接口也被拒绝。
- 管理员可输入但不能重新查看完整网关 Key。
- 页面能够自动同步模型、显示推荐并允许管理员确认。
- 未完成真实能力测试的配置不能发布。
- 发布后新任务使用正式配置，旧任务保持原版本。

### 14.3 可靠性与安全

- 重复保存、同步、测试和发布不会产生重复结果或重复副作用。
- 多账号数据不能互相访问。
- 日志、接口、审计和构建产物不泄露 Key。
- sub2API 故障不影响采集箱、店铺、商品、订单和扩展端。

## 15. 测试与验证计划

实施完成后至少运行：

- 配置合同、权限、账号边界和状态流转单元测试。
- 密钥加密、解密、篡改拒绝、主密钥缺失和不可回显测试。
- 模型列表解析、推荐、同步幂等和计划任务测试。
- 文字与图片能力测试的受控网关测试。
- PostgreSQL 真实迁移、并发发布、版本冲突和审计不可变测试。
- Docker Compose 配置和本地健康检查。
- 前端构建、权限展示、草稿保护和重复点击测试。
- 自动上架任务配置锁定回归。
- 采集箱、店铺、商品、订单和扩展端相关回归。

真实 sub2API、真实上游模型和付费能力测试列为显式人工验收步骤，运行前必须提示可能产生费用，不纳入默认自动化测试。

## 16. 回滚方案

- 通过功能开关关闭 AI 模型配置和自动上架运行时。
- 停止本地 sub2API 容器，不影响其他服务。
- 保留新增表、配置版本和审计数据，避免破坏式回滚。
- 恢复上一版已验证正式配置。
- 应用代码可以回滚到上一版本；追加式数据库迁移保留，后续再用兼容迁移调整。

## 17. 实施顺序

1. 固化本地 sub2API 独立 Compose、版本、端口、健康检查和运维入口。
2. 设计并迁移加密凭据和模型同步数据结构。
3. 实现凭据加密端口及部署密钥加载。
4. 实现模型清单同步、缓存和推荐服务。
5. 扩展现有能力测试与配置发布闭环。
6. 实现管理员配置页面和自动上架入口。
7. 接入每日同步任务和降级提醒。
8. 完成自动化测试、真实本地 smoke test、旧功能回归和回滚演练。

每一步均通过稳定 contract 与现有自动上架模块协作，不允许配置页面、Docker 部署或凭据存储直接耦合采集、商品、订单等旧功能实现。
