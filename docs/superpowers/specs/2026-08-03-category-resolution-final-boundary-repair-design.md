# 类目解析最终边界修复设计

## 目标

关闭账号级 Ozon 类目自动解析最终复审发现的三个生产边界，使 PostgreSQL 手工类目保存、错误分类和凭据缓存并发失效都具备可验证的正确行为。

## 设计

### PostgreSQL 手工类目保存

公开商品对象继续隐藏 `accountId`，避免扩大前端 contract。数据库更新函数在事务内部以独立的、仅供后端回调使用的 `accountId` 参数传递账号上下文；手工类目保存仍与草稿更新、审计写入共用同一个 PostgreSQL transaction client。任一步失败时整个事务回滚。

### 旧快照错误分类

Ozon 类目服务继续保留最后一次有效快照，但解析服务根据 `staleReasonCode` 判断后续动作：超时、限流、5xx 等临时错误进入有界重试；`OZON_CATEGORY_DATA_INVALID` 等确定性响应错误进入 `NEEDS_REVIEW`，不进行无意义重试。旧快照只用于保留证据，不用于匹配。

### 缓存并发失效

类目服务为每个账号与店铺维护单调递增的缓存 epoch。请求开始时捕获 epoch，只有请求完成时 epoch 仍相同才允许写入普通缓存或快照缓存。凭据更新先增加 epoch，再清除对应账号与店铺的缓存，因此旧凭据发出的在途请求即使晚返回，也不能重新污染缓存。其他账号和店铺不受影响。

## 数据与接口边界

- 不修改公开 HTTP 响应结构，不向前端暴露 `accountId`、缓存 epoch 或数据库表字段。
- 不新增破坏性数据库迁移。
- 不改变 Ozon 上架、订单、库存和扩展采集 contract。
- 错误日志与审计继续使用稳定错误码，不记录凭据或原始敏感响应。

## 验收

1. PostgreSQL PATCH 真实事务路径能够保存 `MANUAL` 类目；删除后端账号上下文传递时测试必须失败。
2. 带 `OZON_CATEGORY_DATA_INVALID` 的 stale 快照进入 `NEEDS_REVIEW`；临时 stale 错误仍按计划重试并可恢复。
3. 凭据更新期间的旧在途请求不能写回缓存；新凭据请求返回新树，其他账号/店铺缓存保持可用。
4. 聚焦测试、完整 App + Server active suite、前端生产构建、语法/边界/敏感数据检查通过；配置型跳过和环境阻塞单独报告。
5. 独立只读复审不再发现 Critical 或 Important 问题后，才允许进入集成选择。

## 回滚

修复以独立提交交付。出现问题时回滚该提交即可恢复上一版本；没有数据迁移或真实平台副作用需要撤销。
