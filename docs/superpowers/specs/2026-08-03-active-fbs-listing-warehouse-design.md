# 采集箱活跃 FBS 上架仓库设计

## 目标

采集箱商品编辑页的“上架仓库”只允许选择当前经营店铺下处于活跃状态的 FBS 仓库。数据库继续保留 FBO、FBP、FBS、rFBS、档案仓库及其库存历史，不删除、不迁移现有数据。

## 业务规则

一个仓库必须同时满足以下条件，才属于“活跃 FBS 上架仓库”：

1. 仓库和目标经营店铺属于同一账号、同一店铺数据边界。
2. 仓库类型标准化后严格等于 `fbs`，不能用“不是 fbp”代替。
3. 仓库具有非空的 Ozon `warehouse_id`；数据库内部生成的 `wh_*` ID 不能替代平台仓库 ID。
4. 仓库没有明确的停用或归档证据：`status` 不是 `disabled`、`archived`、`inactive`、`deleted` 或 `blocked`，并且 `is_active` 不是 `false`、`is_archived` 不是 `true`。
5. 当前店铺商品快照中，至少有一个未归档商品的 FBS 库存记录指向该 `warehouse_id`。

第 5 条是本项目对“活跃”的业务定义，不冒充 Ozon 官方仓库生命周期状态。库存数量可以为零；不能因为库存为零就判定仓库不活跃。

按照 2026-08-03 本地数据，预期可选仓库只有：

- `CEL-陆运`
- `CEL-陆空联运`

名称只用于显示和验收核对，不参与资格判断。

## 不在本次范围内

- 不删除或归档任何数据库仓库记录。
- 不删除逐仓商品库存记录。
- 不改变 Ozon 商品、订单、采集箱或库存同步范围。
- 不根据仓库名称、名称前缀或当前库存数量判断资格。
- 不把 UNI 仓库永久写死为档案仓；如果将来它重新关联未归档商品，应自动恢复为可选。

## 方案比较

### 方案 A：后端统一判定并向前端提供资格结果（采用）

后端使用一个纯业务策略统一计算仓库资格，API 为每个仓库附加最小资格结果。采集箱前端只显示 `eligible=true` 的仓库；上架预检和提交再次调用同一策略校验。

优点：只有一个业务依据，前端不能绕过，符合后端权限和业务规则校验要求；不修改数据库。缺点：需要同时调整仓库公开 contract、采集箱显示和上架校验。

### 方案 B：只在采集箱前端筛选

实现最快，但调用方可以绕过页面直接提交 FBO、档案 FBS 或占位仓库，因此不采用。

### 方案 C：把“活跃”结果持久化到仓库表

查询简单，但活跃性会随商品归档状态变化，需要额外状态同步和失效机制，容易产生过期状态，因此不采用。

## 架构与职责

### 1. 活跃 FBS 资格策略

新增一个无数据库副作用的业务策略模块，职责仅包括：

- 标准化店铺、仓库类型、平台仓库 ID 和显式状态。
- 从当前店铺的未归档商品中收集 FBS 库存关系对应的 Ozon `warehouse_id`。
- 对单个仓库返回稳定结果：
  - `eligible`: 是否可用于采集箱上架。
  - `code`: 稳定原因码。

原因码限定为：

- `ELIGIBLE_ACTIVE_FBS`
- `STORE_SCOPE_MISMATCH`
- `TYPE_NOT_FBS`
- `WAREHOUSE_ID_MISSING`
- `WAREHOUSE_DISABLED`
- `NO_ACTIVE_PRODUCT_ASSOCIATION`

策略不读取仓库名称，也不进行网络调用。

### 2. API 公开 contract

认证后的本地状态仓库条目增加一个兼容性字段：

```json
{
  "listingEligibility": {
    "eligible": true,
    "code": "ELIGIBLE_ACTIVE_FBS"
  }
}
```

这是只增不删的 contract 变更。数据库原始字段继续保留，其他页面仍可读取完整仓库数据。API 只能基于当前认证账号可见的店铺和商品计算资格，不能跨账号借用商品关联。

### 3. 采集箱商品编辑页

“上架仓库”下拉框只显示以下记录：

- 属于当前选择的目标经营店铺；
- `listingEligibility.eligible === true`。

页面不再自行通过名称、`warehouse_type !== "fbp"` 或默认 `is_active` 推断资格。没有合格仓库时显示：

> 当前店铺暂无活跃 FBS 仓库，请先完成商品同步。

### 4. 后端上架校验

保存草稿可以保留历史仓库值，但上架预检和正式提交必须重新计算目标仓库资格。请求中的仓库不合格时，后端返回稳定的 `422` 错误，不能创建上架任务，也不能调用 Ozon 上架 API。

错误 contract：

```json
{
  "code": "LISTING_WAREHOUSE_NOT_ELIGIBLE",
  "message": "请选择当前店铺的活跃 FBS 仓库",
  "reason": "TYPE_NOT_FBS"
}
```

服务端不得在错误响应或日志中暴露店铺密钥、原始库存响应或其他账号数据。

## 数据流

1. 商品和仓库继续按现有流程同步并保存完整数据。
2. `/local/state` 等认证响应根据当前账号、当前店铺的商品快照计算每个仓库的 `listingEligibility`。
3. 采集箱编辑页只显示资格为真的仓库。
4. 用户提交预检或正式上架时，后端使用最新状态再次判定，而不是信任前端传入结果。
5. 商品同步完成后，现有状态刷新会重新计算资格；仓库可以随着未归档商品关系变化自动进入或退出下拉框。

## 失败与边界处理

- 商品数据未同步或当前店铺没有未归档商品：所有仓库均不可选，原因是 `NO_ACTIVE_PRODUCT_ASSOCIATION`。
- 仓库只有归档商品：不可选。
- 仓库同时有关联未归档和归档商品：可选。
- FBS 仓库库存为零但仍关联未归档商品：可选。
- FBO、FBP、rFBS：不可选。
- 缺少 Ozon `warehouse_id` 的 `fbs` 汇总或占位记录：不可选。
- 仓库与商品属于不同账号或店铺：不可选，并由后端数据边界校验阻止提交。
- 同步失败时不删除数据；资格继续根据最后一次成功持久化的完整快照计算。

## 测试与验收

### 单元测试

- 类型严格为 FBS、平台 ID 有效、同店铺且关联未归档商品时返回 `ELIGIBLE_ACTIVE_FBS`。
- 仅关联归档商品时返回 `NO_ACTIVE_PRODUCT_ASSOCIATION`。
- 同时关联未归档和归档商品时仍可选。
- 库存为零不影响活跃判定。
- FBO、FBP、rFBS 返回 `TYPE_NOT_FBS`。
- 明确停用或归档的 FBS 返回 `WAREHOUSE_DISABLED`。
- 缺少平台 ID 的占位记录返回 `WAREHOUSE_ID_MISSING`。
- 跨账号、跨店铺记录返回 `STORE_SCOPE_MISMATCH`。

### API 和后端测试

- `/local/state` 对当前账号返回完整仓库数据，但只有符合规则的仓库带有 `eligible=true`。
- 直接构造请求提交 FBO、档案 FBS、占位仓库或其他店铺仓库时，预检和正式提交均返回 `422`，且不创建任务。
- 合格的活跃 FBS 仓库仍可通过现有预检与提交链路。

### 前端测试

- 下拉框只消费后端资格 contract，不再通过名称或“非 FBP”规则判断。
- 当前本地快照只显示 `CEL-陆运` 和 `CEL-陆空联运`。
- 没有合格仓库时显示明确提示且阻止上架。

### 回归范围

- 商品列表与库存展示继续能够读取完整商品和仓库历史数据。
- 店铺切换后只显示目标店铺的合格仓库。
- 类目匹配、采集补全、草稿保存、订单和促销同步不受影响。
- PostgreSQL 和 JSON 持久化模式使用相同资格规则。

## 交付与回滚

本次不包含数据库迁移和数据清理。回滚时撤销资格策略、API 附加字段、前端筛选和后端提交校验即可；数据库数据无需恢复。

完成后必须报告修改文件、API contract、测试结果、未验证范围、回归风险和回滚方式。
